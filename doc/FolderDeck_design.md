## 1. 개요

FolderDeck는 **한 프로젝트에 속한 여러 폴더를 위한 탐색기 여러 개를 한 화면에 펼쳐,
파일·폴더 관리를 창 전환 없이 처리하는 Windows 데스크톱 앱**이다.

프로젝트마다 코드·문서·로그·임시 폴더 등 4~8개를 오가며 생기는 반복 노동(폴더 이름
외워 이동 / 닫았다 다시 열기 / 산출물 옮기기 / 로그 확인 / 임시파일 정리)을 한 워크스페이스로
묶어 없앤다. 프로젝트에 속한 폴더들을 "작업 관리(워크스페이스)" 단위로 묶고, 그 폴더들을
4x4 그리드 배치로 펼쳐 본다.

### 1.1 핵심 용도 (범위 확정)

핵심 용도는 **프로젝트별 탐색기 여러 개 + 파일·폴더 관리**다. AI 코딩 도구(Claude Code
등) 산출물을 제자리로 옮기는 흐름은 대표 사례일 뿐 전부가 아니다. 여기서 두 가지가 따라온다.

- 조작 대상은 파일뿐 아니라 **폴더 자체**를 포함한다. 폴더 복사는 재귀, 다른 볼륨 간
  이동은 실질적으로 복사+삭제이므로 **진행 표시와 취소**가 필요하다(→ Phase 3).

  > **Phase 3 Stage 3 에서 확정한 진행·취소 규칙.**
  > - **취소점은 파일 하나 사이**다(단위 사이 + 폴더 트리를 걷는 중 파일마다 + 하위 폴더마다).
  >   그래서 **파일 하나를 복사하는 도중에는 끊기지 않는다** — 아주 큰 파일 하나면 그 한 개가
  >   끝날 때까지 기다린다. `File.Copy` 를 쪼개 부분 파일을 남기는 것보다 낫다고 봤다.
  > - **같은 볼륨 + 합칠 것 없는 폴더 이동은 이름 바꾸기 한 번**이라 트리를 걷지 않고,
  >   따라서 중간 취소도 없다(원자적이다). 볼륨이 다르거나 합칠 것이 있으면 트리를 걷는다.
  > - **이동의 삭제 단계는 복사가 전부 성공한 뒤에만.** 취소·실패면 원본은 통째로 남는다 —
  >   볼륨 간 이동에서 원본이 반쯤 지워지는 사고를 원천 차단한다.
  > - **취소가 절반 처리 상태를 숨기지 않는다.** 결과 사유에 어디까지 했는지와 목적지에
  >   일부가 남았다는 것을 적는다(예: "취소 — 파일 1834개까지 복사했다. 목적지에 일부가
  >   남았다 (원본은 그대로)"). 남은 부분을 자동으로 지우지는 않는다 — 합치기였다면 원래
  >   있던 것과 방금 넣은 것을 구별할 수 없어 지우는 쪽이 더 위험하다.
  > - 진행 줄은 **0.4초 뒤에도 돌고 있을 때만** 뜬다(낱개 몇 개에 막대가 번쩍이지 않게).
  >   큰 폴더 하나는 단위로 세면 `0/1` 에 멈춰 보이므로 **실제로 만진 파일 수**를 같이 보인다.
- 그리드의 각 타일은 단순 "폴더 내용 표시기"가 아니라 **탐색기 뷰**다. 하위 진입·상위
  이동·우클릭 메뉴가 탐색기와 같은 감각으로 동작한다(§4.6).

### 1.2 명시적 비목표 (v1에서 안 함)
- git 연동: 사용자가 이미 TortoiseGit을 쓰므로 불필요. 넣지 않는다.
- 앱 내 파일 미리보기: 더블클릭 = OS 기본 프로그램으로 열기로 충분.
- 파일 썸네일: **미리보기 그림을 만들지 않는다.** 파일 내용을 읽어 축소판을 그리는 일은 하지
  않는다. 목록 항목에 그려지는 그림은 **셸이 이미 갖고 있는 아이콘**뿐이다(→ §3.2).
- **아이콘 폰트는 쓰지 않는다.** 글꼴 파일을 리소스로 싣지 않는다는 뜻이고, 이것은 그대로다.

  **`familylook_spec` 은 이번에도 고치지 않는다.** 구현은 §3.2 에 산다.
- **확장자별 글리프 커스텀은 그대로 산다**(D59 · §3.3). 다만 **근거를 바꿔 세운다.**
  - ~~사는 근거 — 이미지 리소스를 쓰지 않는다. 그래서 사용자가 고르는 것도 그림 파일이
    아니라 글자 한 자다.~~ — **D68 이 이 근거를 깼다.** 목록 항목에 그림이 그려지게 됐기
    때문이다. **기능은 살고 근거만 바뀐다.**
  - **새 근거** — 사용자가 고르는 것이 글자 한 자인 이유는 이제 「이미지를 안 써서」가
    아니라 **셸이 그림 쪽을 이미 맡고 있어서**다. 사용자가 더할 것은 셸이 못 주는 뜻뿐이고,
    그래서 커스텀이 셸 아이콘보다 **앞선다**(§3.2 의 ① 단).
  - 성립하지 않는 근거 — 「글리프 어휘가 패밀리룩의 일부여서 어휘표가 앱 하나 쪽으로
    비대해진다」. **그 어휘표는 세 앱이 맞추면 좋은 것이지 강제가 아니라고 JH 가 확인했다**
    (2026-08-28).
  - **앱이 정한 어휘는 여전히 두 갈래다**(`📁`/`📄`). **기본 매핑을 깔지 않았다** — 깔면
    그것이 「우리가 정한 어휘」가 되어 위 우려가 진짜가 된다. 매핑이 비어 있으면 사용자가
    보는 것은 **셸이 주는 것 그대로**다.
  - **글리프 색은 확장자를 보지 않는다.** 색이 나르는 뜻은 「폴더 대 파일」 이분법 하나이고,
    파일은 확장자가 무엇이든 같은 색이다. **그 색이 사는 자리는 ③ 단뿐이다**(§3.2).
- **앱 아이콘(exe·창)은 이미지 리소스를 쓴다**(Phase 7 · D46).
  `src/FolderDeck.App/Assets/FolderDeck.ico` 가 이 앱의 유일한 **이미지 리소스**다 — 셸
  아이콘은 리소스가 아니라 **실행 중에 OS 에서 받아 오는 것**이라 이 문장을 깨지 않는다.
  설치본·작업 표시줄·창 제목줄에 기본 아이콘으로 뜨는 것을 막을 다른 수단이 없다. (→ §12)
- 별도 탐색기 창 제어(창 배치 복원): 자체 UI 방향으로 전환하며 폐기.
- 매크로 소스의 패턴 매칭(`*.tmp` 등)은 v1에서 제외(§4.7).

## 2. 핵심 개념

### 2.1 작업 관리 (Workspace)
- 폴더 묶음 + 그리드 배치 + 창 위치를 담는 최상위 단위.
- 속성: 제목(수정 가능), 설명(자유 기입), 폴더 목록, 그리드 배치, 마지막 창 위치,
  마지막 사용 시각.
- 프로그램 시작 시 런처에서 어느 워크스페이스로 시작할지 선택.

### 2.2 폴더 (Folder entry)
- 워크스페이스에 등록된 실제 폴더 하나. **단순 경로가 아니라** 표시 이름·설명·뷰 방식·
  정렬·pin을 가진 개체다.
- 속성: 실제 경로(**앵커**), 표시 이름, 설명, 뷰 방식, 정렬 기준, 상시표시 여부(pin).
- 폴더 안의 파일 목록은 저장하지 않고 열 때 실시간으로 읽는다(파일은 계속 바뀜).

### 2.3 상시 칸 vs 순환 칸 (혼합 모델)
그리드의 각 타일은 두 성격 중 하나를 가진다.
- **상시(고정) 칸**: 특정 폴더를 앵커로 못박아 항상 그 폴더가 보인다. (UI: 실선 테두리)
- **순환 칸**: 왼쪽 폴더 리스트에서 클릭한 폴더가 그 자리에 교체되며 뜬다. (UI: 점선 테두리)

"계속 봐야 하는 폴더(코드)는 늘 펼쳐두고, 가끔 보는 폴더(로그·문서·임시)는 한 자리에서
번갈아 본다"는 요구에서 나온 모델. 왼쪽 리스트가 순환 칸의 컨트롤러를 겸한다.

**순환 칸은 여러 개 둘 수 있고 각자 번호를 갖는다**(순환1, 순환2 …, Phase 2). 폴더도 자기
순환 번호(`rotationSlot`)를 가지므로, 왼쪽 리스트 클릭 하나로 정해진 칸에 뜬다 — 순환 칸이
자기 드롭다운을 갖지 않아도 어디에 뜰지가 정해진다(규칙 전문은 §11).

**성격이 하나 더 늘었다 — 검색 타일**(Phase 12 · D69 · §4.12). 폴더를 담지 않는 타일이라 위
둘 중 어느 쪽도 아니다. **상시 칸처럼 놓은 자리에 못박히지만 폴더를 앵커로 갖지 않는다.**
순환 칸이 될 수 없는 이유는 순환의 정의 자체에 있다 — 순환은 「왼쪽 리스트에서 클릭한 폴더가
그 자리에 뜬다」는 뜻인데 검색 타일에는 폴더가 뜰 자리가 없다. 억지로 허용하면 클릭이 검색
결과를 밀어내거나(되돌릴 손잡이가 없다) 클릭이 무시되거나(순환하지 않는 순환 칸) 둘 중
하나가 된다.

## 3. 화면 구조

### 3.1 런처 화면

**런처는 실행하면 뜨는 워크스페이스 선택 창이다.** 하나를 고르면 **그 창이 그대로 워크스페이스
창이 된다** — 새 프로세스를 띄우지 않고 선택 창도 남지 않는다. 상주하는 런처 프로세스는
존재하지 않는다(Phase 6). 두 번째 워크스페이스는 exe 를 다시 실행하거나 워크스페이스 창의
툴바 버튼(§3.2)으로 연다. 아래 문서 전체에서 「런처」는 이 뜻이다.

- 저장된 워크스페이스 목록. 항목(카드)은 **세 줄**이다(Phase 8-A·8-B) — 1줄 제목 + 설명 ·
  2줄 마지막 사용 시각 + 대표 폴더 경로 · 3줄 폴더 개수 + 상시 폴더 이름(호박) + 순환 폴더
  이름(보라). **그리드 크기는 그리지 않는다** — v1 서술에 있었으나 실제로 그린 적이 없다는
  것이 Phase 8-A 에서 확인됐다.
  - **대표 폴더 경로**는 `folders[0].path` 고, 폴더가 하나도 없으면 워크스페이스 JSON 파일
    경로다. 필터가 보는 값과 같다 — 갈라지면 "보이는데 안 걸린다"가 생긴다.
  - 목록은 인덱스 파일이 아니라 `workspaces\*.json`을 열거해서 만든다(불일치 방지).
- 항목마다 "열기". 제목/설명 편집도 여기서. **열기·수정·삭제 버튼은 가로로 놓인다**(Phase 8-A).
- **카드를 한 번 누르면 선택(하이라이트), 두 번 누르면 연다**(Phase 8-A). 여는 경로는 "열기"
  버튼과 같은 하나라 §6.2 판정이 더블클릭에도 그대로 걸린다.
- **하단 고정 바**(Phase 8-A). 스크롤 영역 밖이라 목록이 길어도 늘 보인다. 맨 왼쪽에
  `＋ 새 작업 공간`, 그 옆에 "마지막 작업을 자동으로 열기(런처 건너뛰기)".
- **탐색기에서 폴더를 런처 창에 끌어다 놓으면 "새로 만들기"로 이어진다.** Phase 1+2 부터 있던
  동작인데 문서에 적히지 않아 Stage 0 에서 발견했다(§9 의 Phase 5 서술과 함께 볼 것).
  **네트워크 폴더를 이렇게 끌면 바로가기 파일 위치가 등록된다**(2026-08-12 손 확인). 직접
  폴더 추가로 찾아 넣으면 정상이다. **`.lnk` 를 어떻게 풀지에 대한 규칙이 이 문서에 없다** —
  고치는 것은 뒤 일감이다.
- **"삭제"는 작업 관리(워크스페이스)만 지운다.** 실제 폴더는 건드리지 않는다는 것을
  버튼/확인창 문구에 명시한다.
- **항목마다 열려 있는지 표시한다**(Phase 4 Stage 1 · Phase 6 개정). `● 열려 있음` 배지와 함께
  버튼 글씨가 `열기` ↔ `열려 있음` 으로 바뀐다. 이미 열린 것을 눌러도 **아무 일도 일어나지
  않으므로**(§6.2), 누르기 전에 화면이 그것을 말해 "눌렀는데 아무 반응이 없다"는 순간을
  없앤다(§4.3 충돌창과 같은 원칙). 색만으로 구분하지 않는다 — 글자가 있어야 한다.
  - **배지는 힌트고 판정은 누를 때다.** 낡아도 누르면 맞는 동작이 나온다(열려 있으면 아무 일도
    하지 않고, 닫혀 있으면 새로 연다). 누를 때 재확인 결과가 배지와 다르면 재확인 쪽을 따르고
    배지를 고친다.
  - **폴링하지 않는다.** 선택 창 활성화 시 재검사 + 누르는 순간 재확인 둘뿐이다(§8 의 기존 결).
  - 이 상태는 저장하지 않는다(런타임 판정뿐).
- ~~**런처는 워크스페이스를 열어도 닫히지 않고 상주한다**(Phase 4 Stage 1)~~ — **Phase 6 에서
  뒤집혔다.** 고르면 그 창이 워크스페이스 창이 된다(위 재정의). 상주를 택했던 근거는 「여러
  프로젝트를 연속으로 열 자리」였으나 그 자리는 §3.2 툴바 버튼과 exe 재실행이 갖는다. 뒤집은
  이유는 따로 있다 — 상주 런처는 워크스페이스보다 **위에 있는 층**이 되어, FolderDeck ·
  TerminalDeck · WebDeck 을 하나로 묶는 프로젝트 층과 층이 겹친다. Phase 1~3 은 같은 프로세스에서
  창을 바꿨고 Phase 6 은 그 구조로 돌아간다.

### 3.2 메인 화면
좌우 2단 구성.

**왼쪽 컬럼 (상하 2분할)**
- 위: 폴더 리스트 = 유일한 컨트롤러.
  - 각 폴더 행에 pin 표시(상시=실선 pin / 순환 전용=점선 글리프)와 설명.
  - 클릭 → 그 폴더가 자기 번호의 순환 칸에 표시. **같은 폴더를 다시 클릭 = 앵커로 리셋.**
  - 단, **이미 상시 칸에 못박혀 있는 폴더는 순환 칸을 쓰지 않는다** — 그 폴더의 상시 칸이
    앵커로 되돌아올 뿐이다(§4.1). 그런 행에는 순환 번호 태그도 붙지 않는다.
  - 타일이 앵커를 벗어나 하위 경로에 있으면 그 상태를 행에도 표시(예: "지금 src › Recipe 안").
  - 접근 불가 폴더는 목록에서 지우지 않고 상태만 표시(§5 이하).
  - **헤더에 「＋」, 각 행에 「✕」가 있다**(D38 · → §4.11). 등록과 제거의 눈에 보이는 자리다 —
    「✕」는 그 행을 가리키거나 초점이 갔을 때만 나타나고, 배치 편집 중에는 뜨지 않는다(D39).
- 아래: **`복사 대상함` / `매크로` 2탭.**(3단 분할은 폴더 리스트를 눌러서 안 함.)
  - 대상함: 자주 쓰는 목적지 폴더 상주. 체크된 폴더가 복사/이동 목적지. 다중 체크 = 동시 복사.
  - 매크로: 저장된 규칙 카드 목록(§4.7).

**오른쪽 컬럼 (4x4 그리드)**
- 16칸. 폴더 타일이 여러 칸 차지(1x1 ~ 4x4).
- 각 타일은 상시 칸(실선) 또는 순환 칸(점선). **색은 뜻 하나씩** — 호박색=상시, 보라=순환.
  테두리 실선/점선으로 색 없이도 구분(색맹 대비).
- 타일 헤더는 **한 줄**이다(Phase 8-C). 왼쪽에 **breadcrumb**(앵커 이름 › 하위…) + 항목 개수,
  오른쪽에 상위/앵커 복귀 버튼과 아이콘들. **고른 개수도 이 줄에 붙는다**(`5개 · 1개 선택`,
  Phase 8-D) — 선택했다고 헤더 높이가 뛰지 않게 하려는 것이다.
  - 뷰 방식은 **아이콘 토글**이다(`☰` list ↔ `▦` details) — 누르면 바뀌고 **전환하면 선택이
    비워진다**(§4.8).
  - 정렬은 **아이콘이 메뉴를 연다**(`▴` 오름 / `▾` 내림. 「폴더 먼저」를 끄면 앞에 `∪`).
    **뷰 전환과 달리 정렬 변경은 선택이 살아남는다**(§4.8).
  - **정렬 기준(이름·수정·크기·종류)에는 글리프를 붙이지 않는다.** 넷을 다 붙이면 글리프
    어휘표가 이 앱 쪽으로 비대해진다(`doc/FolderDeck_familylook_spec.md` §6). 기준은 툴팁과
    메뉴의 체크가 말하고, 상세 뷰에서는 컬럼 머리글이 「이름 ▴」로 적는다.
  - **상세 뷰는 컬럼 머리를 눌러도 정렬된다**(Phase 8-B). 같은 컬럼을 다시 누르면 방향이
    뒤집힌다 — 정렬 메뉴가 쓰던 경로를 그대로 부른다.
  - **「폴더 먼저」를 끄면 폴더와 파일이 섞여 정렬된다**(Phase 8-B). **크기 기준만은 꺼도 폴더가
    앞에 뭉친다** — 폴더 크기를 재귀로 재지 않아(§2.2) 값이 없기 때문이다. 결함이 아니다.
  - **재귀 검색 중에는 잠긴다** — 결과가 발견 순서라 기준만 바뀌면 표시가 거짓말이 된다(§4.10).
- 헤더 **둘째 줄은 말할 것이 있을 때만** 나온다(Phase 8-D) — 「앵커 밖」·「읽는 중…」.
  고른 개수는 여기 있었으나 1줄로 옮겼다. 선택할 때마다 줄이 생겼다 사라져 헤더가 뛰었다.
- 목록 항목의 아이콘은 **3단**이다(Phase 11 · D68) — **① 확장자 커스텀(§3.3)이 있으면 그
  글자 → ② 없으면 셸 아이콘 → ③ 셸도 못 얻으면 `📁`/`📄` 글리프.**
  - **폴더도 셸 아이콘을 받는다.** 목적이 「탐색기와 같은 모양·색」인데 폴더만 빼면 목적을
    반쯤 버린다.
  - **셸 호출은 비동기다.** UI 스레드에서 동기로 부르지 않는다. 아이콘이 도착하기 전 그
    자리에는 **③ 단이 서 있는다** — 빈칸을 두면 도착할 때마다 줄이 뛴다.
  - 목록은 가상화(Recycling)라 **보이는 줄만** 아이콘을 평가한다(§8).
- **글리프 색은 ③ 단에서만 산다** — 폴더 황토(`Brush.FolderGlyph`) · 파일 무채색
  (`Brush.FileGlyph`). Phase 8-C 가 이 색을 넣은 이유는 WPF 가 컬러 폰트를 그리지 않아 두
  글리프가 같은 굵기의 가는 윤곽선으로 떨어지기 때문이었고, **그 이유는 ③ 단에 그대로
  남아 있다.** ①·② 단에서는 색이 각각 사용자가 고른 글자와 셸 아이콘 자신의 것이다.
  **브러시 둘을 지우지 않는다** — 셸을 못 얻는 경로가 살아 있는 한 쓰인다.
  - **색만으로 구분하는 것이 아니다** — 이름 글자가 늘 붙어 있고 상세 뷰는 크기 칸이
    폴더만 비어 있다.
- 하단 상태 바: 순환 칸의 전체 경로(타일 헤더가 좁아 잘리므로 전체 경로 볼 자리).
- 파일 목록을 폴더의 뷰 방식대로 표시.
  - 열 구성은 뷰 방식마다 다르다 — 상세 뷰는 `이름`·`크기`·`수정`, 검색 결과 뷰(§4.10)는
    `이름`·`위치`·`크기`·`수정`. **폭은 고정이 아니다.**
- **컬럼 폭 자동 조절.** 타일 폭이 바뀌면 컬럼 폭을 다시 잡는다. **늘리고 줄이는 컬럼은 뷰마다
  하나**고(상세 `이름` · 검색 `위치`) 나머지는 시작값 그대로다.
  - 오른쪽에 **여백 32px** 을 일부러 남긴다 — 고무줄을 시작할 자리다(§4.8). 판정에 필요한 폭은
    4px 이고 32px 는 손으로 집을 폭으로 **정한 값**이다.
  - 계산에 **행 테두리 6px** 이 들어간다(컬럼 합 480px → 행 486px). 안 빼면 여백이 26px 이 된다.
  - 늘어나는 컬럼의 **최소 폭은 160px** 이다. 거기서 멈추면 남는 것은 가로 스크롤로 흐른다 —
    **타일 폭 463px 아래에는 여전히 가로 스크롤이 있다**(1x1 타일도 그렇다).
  - **줄기도 한다.** 시작값은 상한이 아니다 — 타일 폭 464px 에서 상세 뷰 `이름` 은 260px 에서
    161px 로 줄어든다. 가로 스크롤이 고무줄과 드래그를 다 방해하므로 좁히는 쪽을 택했다.
  - 검색 결과 뷰의 `이름` 은 220px 에 못박혀 있어 넓은 타일에서는 `위치` 만 커진다(타일 900px 이면
    `위치` 가 400px 대). "늘릴 컬럼 하나" 규칙 그대로지만 균형이 이상해 보일 수 있다.
  - **사용자가 헤더를 끌어 바꾼 폭은 기억되지 않는다** — 막지도 저장하지도 않고 다음 크기 변화에
    덮인다.
- **어느 열을 볼지 고른다**(Phase 15 · D79). 상세 뷰에서 `크기`·`수정` 을 각각 끄고 켤 수 있다.
  **`이름` 은 끌 수 없다** — 이름이 사라지면 목록이 목록이 아니다.
  - **폭 저장이 아니라 표시 토글이다.** 작은 타일에서 폭을 끌게 되는 이유가 「이름을 더 길게
    볼 때도, 크기를 없애고 수정 날짜 위주로 볼 때도 있다」였다 — 하고 있는 것은 폭 조절이
    아니라 **어느 열을 볼지 고르는 것**이고, 폭 드래그는 열을 없앨 방법이 없어 쓰는 대용품이다.
  - **자동 폭 계산을 한 줄도 고치지 않는다.** 고정 컬럼 합이 줄면 늘어나는 컬럼이 그만큼
    넓어진다. 폭을 저장하는 쪽으로 가면 자동 계산과 **같은 값을 두고 싸워** 「사용자가 손댔다」
    표식을 새로 만들어야 한다.
  - **진입점은 컬럼 머리글 우클릭 체크 메뉴다**(§4.6).
  - **`GridView` 인스턴스가 생길 때마다 다시 먹인다.** 두 `GridView` 는 `x:Shared="False"` 라
    조회마다 새 인스턴스가 나온다 — 하나를 여러 `ListView` 가 나눠 쓸 수 없기 때문이다(§8).
    한 번 빼 두는 것이 아니라 **뷰가 만들어질 때마다 적용하는 것**이다. 이것을 놓치면 뷰
    토글·검색 전환 뒤에 숨긴 열이 되살아난다.
  - **`위치` 열이 붙는 뷰는 둘이다** — **재귀 검색**(§4.10, 폴더 타일이 검색 중인 것)과
    **검색 타일**(§4.12). 판정은 `NeedsLocationColumn` 하나이고 **토글도 그 둘 다에서
    먹어야 한다.** D79 는 이것을 「검색 타일」 하나로 좁혀 짜서 **재귀 검색에서 `위치` 를
    꺼도 아무 일이 안 일어났다** — D80-b 가 고쳤다. **메뉴 항목이 보이는 조건과 그 항목이
    먹는 조건은 같아야 한다.**
  - **검색 뷰도 토글할 수 있으나 기억하지 않는다.** `위치`·`크기`·`수정` 이 대상이고
    `이름` 은 여기서도 끌 수 없다. `크기`·`수정` 은 폴더 타일이면 그 폴더에 저장되지만
    (재귀 검색 중이어도 마찬가지다), **`위치` 는 어느 경우에도 저장되지 않는다**(§7.1 v8).
    앱을 다시 열면 `위치` 는 다시 보이는 상태로 돌아온다.
  - **열을 다 켠 채 이름만 넓히고 싶은 경우는 이 안으로 안 풀린다.** 타일 폭 463px 아래는
    열을 다 켜면 여전히 가로 스크롤이다. 그 경우의 답은 열 하나를 끄는 것이다.
- 순환 칸에는 번호 태그(순환1, 순환2 …)가 붙고, 아직 아무 폴더도 안 뜬 칸은
  "순환2 — 폴더를 지정하세요"로 비어 있다.
- **"배치 편집" 모드**(툴바 토글): 켜면 격자 경계와 타일 손잡이가 드러나고 타일을 끌어
  옮기거나 오른쪽 아래 모서리로 크기를 바꿀 수 있다. 격자에 스냅하며 4x4 밖으로 나가거나
  다른 타일과 겹치면 **거부**한다(밀어내지 않는다 — 한 번의 드래그가 배치 전체를 흔들면
  무엇이 어디로 갔는지 예측할 수 없다).
  겹치는 자리에 놓으려 하면 **놓기 전에 색으로 미리 보인다** — 끌고 가서 거절당하기 전에 알게 한다.
  우클릭으로 상시↔순환 토글과 타일 제거.
  빈 칸은 클릭(폴더 선택) 또는 왼쪽 리스트에서 끌어다 놓기로 채운다.
  편집 중에는 **파일 목록이 잠긴다** — 실수 클릭으로 파일을 건드리지 않게.
  평소(뷰 모드)엔 타일이 못박혀 파일 작업 중에 배치가 흔들리지 않는다.
  - **타일 사이 여백을 다섯 값 중 고른다**(D56) — `4 / 6 / 8 / 12 / 16` px, 기본 **8**.
    고르개는 이 모드의 툴바에 있다. 밀도는 배치의 성질이고, 평소 모드에 컨트롤을 늘리지
    않는 편이 바로 위 문장과 맞는다. 고르면 **그 자리에서 다시 그려진다** — 「다시 그려라」
    코드는 없고 바인딩이 새 값을 받는다.
    - 다섯은 `familylook_spec` §5 치수 램프다. 램프는 **눈에 보이는 간격**에 먹인다 —
      칸 여백에 먹이면 간격이 그 두 배가 되어 **지금보다 좁아질 수가 없다.**
    - **간격을 만드는 것은 격자가 아니라 칸에 들어가는 요소의 여백이다.** 네 층(타일 ·
      빈 칸 · 편집 손잡이 · 드래그 미리보기)이 각자 **간격의 절반**을 두르고 이웃한 두 겹이
      겹쳐 간격이 된다. 그래서 **격자 둘레는 이웃이 없어 절반**이다 — 그 비율을 그대로 둔다.
      **넷은 함께 움직여야 한다.** 하나만 어긋나면 드래그 미리보기가 실제 타일과 다른 자리에
      그려진다.
    - **절반을 세는 자리는 컨버터 하나뿐이다.** 네 자리에 각각 나눗셈을 쓰면 하나만 고쳐지는
      사고가 난다(§4.9 와 같은 결).
    - 저장은 워크스페이스가 아니라 **전역 `settings.json`**(§7.2)이다. 밀도는 사람의 취향이지
      워크스페이스의 성질이 아니다.
- **같은 폴더를 상시 칸 둘에 두지 않는다.** 이미 상시 칸에 있는 폴더를 빈 칸에 또 넣으려
  하면 거부하고 이유를 말한다(16칸을 낭비할 뿐이고, "겹침=거부"와 같은 결). 폴더 선택
  목록에서도 고를 수 없게 두되 목록에서 지우지는 않고 "이미 상시 칸"이라고 적는다.
  순환 칸은 폴더를 못박지 않으므로 이 규칙과 무관하다.
- **빈 칸에 넣는 것이 폴더만은 아니다**(Phase 12 · D69). 팝업 **맨 아래**, 구분선 뒤의
  「빈 순환 칸 만들기」 **옆에 「전역 검색」**이 붙는다(§4.12). 고르면 그 칸이 검색 타일이 된다.
  - **위가 아니라 아래인 이유** — 이 팝업은 이미 「폴더가 아닌 선택지」를 아래에 모아 둔다
    (순환 칸이 거기 있다). 검색도 폴더가 아니므로 같은 자리다. 맨 위에 두면 제목 바로 밑에
    폴더 아닌 것이 오게 된다. **D69-a 가 「맨 위」로 적었던 것을 D69-e 에서 실물을 보고
    고쳤다.**
  - 팝업 제목은 **「이 칸에 넣을 것」**이다. 「넣을 폴더」는 순환 칸이 붙은 시점부터 이미
    조금 어긋나 있었다.
  - **왼쪽 폴더 리스트에는 붙이지 않는다.** 거기는 폴더의 자리고, 끼워 넣으면 §4.11-4 의
    「두 팝업이 같은 목록을 본다」가 깨진다 — 한쪽에만 있는 항목이 생기는 것이다.
  - **워크스페이스에 하나만 둔다.** 이미 있으면 팝업에서 고를 수 없게 하고 「이미 있다」고
    적는다 — 목록에서 지우지 않는 것은 「이미 상시 칸」과 같은 처리다. **근거는 다르다**:
    16칸이 아까워서가 아니라 Everything 이 검색 조건도 결과도 프로세스에 하나만 갖기
    때문이다(§4.12).
  - **우클릭의 상시↔순환 토글이 이 타일에는 뜨지 않는다**(§2.3). 순환 번호 태그도 안 붙는다.
    옮기기·크기 바꾸기·타일 제거는 폴더 타일과 같다.
- 툴바에 **`다른 작업 관리 열기`**(Phase 4 Stage 1 · Phase 6 개명). 누르면 **새 프로세스를 띄워
  선택 창을 연다**(§3.1). 런처가 상주하지 않게 된 뒤로 이것이 두 번째 워크스페이스를 여는 주
  경로다 — exe 를 손으로 다시 실행하지 않아도 된다. `skipLauncher`(§7.2)가 켜져 있어도 이 경로는
  막히지 않는다. 성공하면 "선택 창을 띄웠다"를 정보성(사라지는) 안내로 남긴다.

### 3.3 설정 창 — Phase 10
- **툴바 오른쪽의 「설정」 버튼**으로 연다(「배치 편집」 왼쪽). 탭 컨트롤 하나를 두었고
  탭은 **「아이콘」·「검색」 둘**이다 — 「검색」은 D65 가 Everything 연동을 넣으며 뒤에
  붙였다. 설정 파일이 손상돼 쓸 수 없으면 버튼이 잠긴다
  (§3.1 의 `skipLauncher` 토글과 같은 게이트).
- **기존 설정 둘을 아직 옮기지 않았다** — 런처의 `skipLauncher` 체크박스(§3.1)와 배치 편집
  툴바의 타일 간격 고르개(§3.2)는 제자리다. 창을 세우는 회차에 함께 옮기면 「아이콘이
  생겼다」와 「고르개가 사라졌다」가 한 화면에서 동시에 일어나 **무엇이 깨졌는지 못 가른다.**
  옮기는 것은 별도 회차의 몫이다.
- **「아이콘」 탭은 행 목록이다.** 행 하나가 「확장자 칸 · 글자 칸 · 미리보기 칸 · `✕`」이고
  `＋` 로 빈 행을 더한다. **빈 행을 만들어 그 자리에서 타이핑하는 패턴은 이 앱에 없던 것이라
  새로 짰다** — 목록과 제거는 런처의 새 워크스페이스 폴더 목록을, 행 안 텍스트 편집은 런처
  카드의 수정 모드를 본떴다(둘 다 §3.1).
  - **미리보기 칸이 두부(`□`)를 막는 대신 보이게 한다.** 넣은 글자를 그 자리에 그대로
    그리므로 글꼴이 못 그리는 글자면 즉시 눈에 띈다. **글리프가 있는지를 코드로 판정하지
    않는다** — 그 자체가 별도 일감이고, 보여 주는 것으로 충분하다. 창 루트 글꼴에
    `Segoe UI Emoji, Segoe UI Symbol` 폴백을 명시해 두었다(D59).
  - 저장하면 **이미 떠 있는 타일들도 그 자리에서 다시 그려진다.** F5 를 누를 필요가 없다.
    취소하면 아무것도 건드리지 않는다.
- 매핑은 워크스페이스가 아니라 **전역 `settings.json`**(§7.2)에 산다. 어느 확장자를 어떤
  글자로 볼지는 사람의 취향이지 워크스페이스의 성질이 아니다.
- **「아이콘」 탭에 셸 아이콘 토글이 붙는다**(Phase 12 · D69 · §7.2). 끄면 3단의 ② 단을
  건너뛰어 ① → ③ 이 된다(§3.2). D68 이 미뤄 둔 것이고, D69 가 어차피 `settings.json` 을
  올리므로 같은 판에 얹어 **판이 두 번 오르는 것을 막는다.**
- **「검색」 탭은 상태 한 줄뿐이었다.** D69 가 **결과 상한 고르개**를 더한다(§4.12). 상태
  문구도 **다섯으로 늘어난다** — 지금 셋(DLL 없음 · 안 떠 있음 · 돌고 있음)은 두 상태를
  「돌고 있음」으로 뭉갠다: **본체는 떴으나 색인이 아직 안 올라온 상태**와 **질의 API 를 갖지
  않은 낡은 판**이다. 둘 다 그대로 검색하면 결과가 비거나 아예 못 부르는데 화면은 정상이라고
  말한다.

## 4. 상호작용

### 4.1 폴더 표시 제어
- 왼쪽 리스트 클릭 → 그 폴더의 `rotationSlot` 번호 순환 칸에 표시(교체).
  같은 폴더 재클릭 → 앵커로 리셋.
- 상시 칸은 지정 폴더를 항상 표시(클릭과 무관).
- **상시 칸에 못박힌 폴더를 클릭하면 순환 칸을 건드리지 않고 그 상시 칸이 앵커로 돌아온다.**
  (Phase 2 에서 바뀐 규칙 — Phase 1 은 성격 무관하게 순환 칸에 띄웠다.)
  이유: 타일 배치가 실제로 생기고 나니, 화면에 이미 떠 있는 폴더를 순환 칸에 또 띄우면
  순환 칸 한 자리를 헛되이 쓴다. 대신 하위로 들어가 있던 상시 칸을 집으로 부르는 데 쓴다.
  이미 앵커에 있어 아무 일도 안 일어나면 상태 바가 왜 그런지 말해 준다.

> **각주 — 상시 칸의 탐색 위치는 이 클릭으로 사라진다.** 상시 칸이 하위 폴더로 깊이
> 들어가 있을 때 왼쪽에서 그 폴더를 클릭하면 앵커로 리셋되며 그 깊이가 없어진다.
> 알고 남긴 동작이다: 이 클릭의 뜻이 "집으로"인데 조건에 따라 안 돌아가면 규칙이 둘이 되고,
> 앵커 복귀 경로(§4.6의 3곳)가 하나 줄어든다. 되돌리려면 하위로 다시 들어가면 되고
> (히스토리 `Alt+←` 로도 된다), 그 비용은 한 번의 클릭이다. 깊이를 지키고 싶으면
> 리스트를 누르지 말고 타일 안에서 작업하면 된다.

### 4.2 파일·폴더 이동/복사 — 두 방식 병행 + 매크로
1. **대상함 방식**: 그리드에서 여러 개 선택(Ctrl/Shift·고무줄 §4.8) → 대상함 목적지 체크 → 복사/이동.
   다중 대상 → 다중 폴더 동시 처리.
2. **드래그앤드롭**: 그리드의 항목을 **다른 타일** · 왼쪽 폴더 리스트 항목 · 대상함으로 끌어다 놓기.
   즉흥적인 단건/소수 이동용. 규칙은 Phase 3 Stage 3 에서 아래로 확정했다.
   - **끌 수 있는 것은 그리드(타일)의 항목뿐이다.** 왼쪽 폴더 리스트의 **행 자체**를 끄는 것은
     이 규칙이 아니라 **배치 편집 모드에서 타일 빈 칸을 채우는 수단**이고(§3.2·§4.11), 평소
     모드에서는 드래그가 시작되지 않는다. 문서가 이것을 적지 않아 「받는 자리 셋」과 혼동된
     적이 있다(D52).
   - **언제 드래그로 보는가**(D70~D72). 누른 자리에서 가로·세로 어느 한 축이라도
     `SystemParameters.MinimumHorizontalDragDistance`/`MinimumVerticalDragDistance` 를
     넘으면 드래그다 — **앱이 만든 숫자가 아니라 OS 값**이라 다른 앱과 같은 손맛이 된다.
     시간은 보지 않는다.
     - **판정은 패널에 걸린 터널링 핸들러가 한다 — 항목(`ListViewItem`)이 아니다**(D71).
       원래는 항목 컨테이너에 걸려 있었는데, 그러면 **커서가 그 항목 밖으로 나가는 순간
       핸들러가 안 불린다.** 파일을 다른 타일로 끌려면 커서가 목록 밖으로 나가야 하고,
       빠르게 튕기면 마우스 이동 표본이 성겨 행 하나(20px 남짓)를 한 표본에 건너뛴다 —
       그래서 **빠르게 끌면 아무 일도 안 일어나고 천천히 끌면 되는** 증상이 났다. 패널은
       커서가 그 안 어디에 있든 불린다. **다시 항목으로 내리지 마라.**
     - **마우스 캡처를 걸지 않는다.** 캡처는 놓는 자리가 넷이라(뗄 때 · 드래그 시작 직전 ·
       실을 것이 없어 되돌아갈 때 · 캡처를 빼앗겼을 때) 하나만 빠뜨려도 **마우스가 잡힌 채
       남아 앱이 클릭을 전부 먹는다.** 고무줄(§4.8)은 캡처를 걸지만 그쪽은 놓는 자리가
       `EndBand` 하나로 모여 있다.
   - **무엇이 끌리는가는 「누른 항목」이 정한다**(D72). 임계를 넘은 순간의 선택 목록을 그대로
     싣지 않는다 — 누른 뒤 임계를 넘기까지 사이에 선택이 바뀌면 **누른 것과 다른 파일이
     끌려가고, 놓으면 그 파일이 실제로 움직인다.**
     - 누른 항목이 **선택 안**에 있으면 선택 전체를, **선택 밖**이면 그 항목 하나만 싣는다.
       **선택이 비어 있어도** 누른 항목 하나를 싣는다 — 마우스 다운 핸들러는 터널링이라
       `ListView` 가 선택을 갱신하기 **전에** 돌고, 그래서 아무것도 안 고른 목록에서 곧장
       끌면 그 시점 선택이 아직 비어 있다. 예전에는 이 경우 드래그가 아예 시작되지 않았다.
     - 판정은 뷰가 아니라 **패널 뷰모델**에 있다. 마우스 제스처 자체는 시험이 못 물지만(§8)
       이 판정은 문다.
   - **탐색기와 같은 규칙이다**(Phase 9 에서 맞췄다) — `Ctrl` 은 복사, `Shift` 는 이동,
     `Ctrl`+`Shift` 는 복사, **아무것도 안 누르면 같은 볼륨이면 이동 · 다른 볼륨이면 복사**다.
     판정은 **놓는 순간**의 수정키로 한다 — 끌기 시작할 때 무엇을 눌렀는지가 아니다.
     끌다가 마음을 바꿀 수 있어야 한다.
     - **원래는 볼륨을 보지 않고 늘 이동이었다.** 「탐색기 관용」이라고 적어 두었으나 실측
       (2026-08-27 · 탐색기 창 ↔ 탐색기 창)에서 탐색기는 **다른 볼륨이면 복사**였다.
       `D:` 에서 NAS 로 끌면 로컬 원본이 사라지는 자리였고 이 경로에는 확인창이 없다.
     - **판정 단위는 뭉치다.** 한 드롭에 서로 다른 볼륨의 항목이 섞이면 **하나라도 다르면
       전부 복사**다. 항목마다 가르면 한 번 누른 것이 조작 둘이 된다(§4.3 과 같은 결).
     - **`Ctrl`+`Shift` 가 복사인 것은 애매한 조합을 되돌릴 수 있는 쪽으로 떨어뜨린 것이다.**
       탐색기에서는 바로가기 만들기인데 이 앱에는 그 동작이 없다.
     - **볼륨은 경로 루트로 가른다.** `subst` 드라이브와 마운트 포인트에서는 탐색기와
       어긋날 수 있다 — 그 둘에서 탐색기가 무엇을 하는지 **재지 않았다.** 어긋나도 동작이
       위험해지지는 않는다(엔진이 볼륨을 넘는 이동을 이미 안다). 어긋나는 것은 정책뿐이다.
   - **확인창을 띄우지 않는다**(대상함 버튼의 이동과 다르다). 드래그는 손으로 과녁을 겨눈
     한 번의 동작이라 "무엇을 어디로"가 이미 눈앞에 있고, 매번 대화상자가 뜨면 이 경로의
     존재 이유(즉흥적인 단건 이동)가 없어진다. 대신 결과를 상태 바에 반드시 적는다.
   - **받지 않는 자리는 과녁을 켜지 않는다** — 끌고 가서 거절당하는 것보다 처음부터 받지
     않는 편이 낫다(Phase 2 "겹침=거부"와 같은 결). 받지 않는 조합은 셋이다:
     ① 온 곳과 같은 폴더(무동작 — 원본을 건드리지 않는다), ② 폴더를 자기 자신이나 자기
     하위로, ③ 다른 조작이 도는 중.
     **①의 판정 단위는 항목이다**(Phase 5 Stage 1 에서 셸 드롭과 통일했다 — §4.9). 뭉치의
     출처는 패널 하나라(§4.8) 대개 전부 같은 폴더여서 뭉치째 거절한 것과 결과가 같지만,
     **하위 폴더까지 포함해 검색한 결과를 끌면 다르다**(§4.10) — 목적지와 같은 폴더인 항목만
     빠지고 나머지는 처리된다. 예컨대 상위 폴더를 보며 검색한 결과를 그 상위 폴더에 놓으면
     하위에 있던 것들이 그 폴더로 모인다. **예전에는 통째로 거절했다** — 옮길 데가 있는데
     막은 것이라 바뀐 쪽이 맞다고 봤다.
   - 과녁 강조는 Phase 2 빈 칸과 같은 파랑 + **결과를 말하는 글귀**다 — `여기로 이동` /
     `여기로 복사`(Phase 9). 규칙이 조건부가 되어 손동작만으로는 무엇이 될지 알 수 없고
     확인창은 두지 않기로 한 자리라 **말하는 일은 과녁이 진다**(§3.1 배지와 같은 결).
     **받는 자리 셋이 다 글귀를 갖는다** — 대상함에는 없던 것을 Phase 9 에서 만들었다.
     글귀는 한 곳에서 만들고 세 자리가 읽기만 한다.
   - 대상함에 놓으면 **그 항목 하나**로만 간다 — 체크된 목적지 집합(버튼 실행)과 섞이지 않는다.
3. **매크로**(§4.7): 저장된 규칙을 한 번에 실행.

세 방식은 모두 `대상 집합 × 목적지 집합 × 동작`이며, **Core의 단일 실행 엔진** 위에
얹힌다(§4.7·§10). 폴더가 대상이면 재귀 복사/이동이 되고 진행·취소가 필요하다.

**이동은 목적지가 하나여야 한다.** 파일 하나가 두 곳에 동시에 있을 수는 없다 — 그대로
실행하면 첫 목적지로 옮겨진 뒤 나머지가 전부 "원본이 없다"로 실패한다. UI 가 목적지 2개
이상에서의 이동을 거부하고 이유를 말한다("여러 곳에 두려면 복사"). 요약 줄도 누르기 전에
미리 알린다. **엔진 자체는 시키는 대로 실행한다** — 판단은 진입점(UI·매크로)의 몫이다.
복사는 다중 목적지가 정상이며 그것이 대상함의 존재 이유다.

앱 경계를 넘는 드래그(탐색기에서 끌어오기 / 탐색기·브라우저로 끌어내기)는 §4.9 에서 다룬다.

### 4.3 동일 이름 충돌

**Phase 3 Stage 4 에서 "겹칠 때만 묻는다"로 바꿨다.** 원래는 "기본 덮어쓰기 + 사후 알림,
차단하지 않음"이었다. 그때는 결과 모델이 없어서 일단 덮고 알려 주는 것이 최선이었지만,
Stage 1 의 미리보기가 **실행 전에 몇 건이 겹치는지 정확히 세므로** 사후 통보로 남길 이유가
없어졌다. 엔진은 처음부터 세 정책을 다 할 줄 알았고(§4.7 `onConflict`), 고를 자리만 없었다.

- **겹치는 것이 하나도 없으면 아무 창도 뜨지 않는다.** 대부분의 복사·드래그가 여기 해당한다.
- 하나라도 겹치면 창 하나를 띄우고 셋 중 고르게 한다 — **덮어쓰기 / 건너뛰기 / 둘 다 두기**
  (+ 취소). 버튼 글씨가 곧 동작이다. 기본 단추(Enter)는 지금 정책에 맞춘다.
  - 덮어쓰기 — 기존 파일을 새 것으로. 결과에 "덮어씀 N"으로 잡힌다.
  - 건너뛰기 — 같은 이름은 손대지 않는다. 결과에 "건너뜀 N".
  - 둘 다 두기 — `a.txt` 옆에 `a (2).txt`. 탐색기와 같은 감각.
- 창에 **"이 작업 관리에서는 다음부터 묻지 않기"** 체크가 있다. 켜면 그 선택이
  워크스페이스(`onConflict`·`askOnConflict`, schemaVersion 4)에 저장되고 이후 조용히 적용된다.
- **묻지 않기로 해 둔 상태는 대상함에 늘 한 줄로 보인다**("같은 이름이 있으면 건너뛴다
  (묻지 않음)") + `다시 묻기` 링크. 잊고 조용히 덮어쓰는 상태가 생기지 않게 하려는 것이다.
  되돌려도 고른 정책은 남는다 — 다음에 물을 때 기본 단추로 쓰인다.
- **기본값은 덮어쓰기**다(아무것도 안 정했을 때). AI 도구 산출물을 제자리로 옮기는 흐름에서는
  새 것이 옛 것을 대체하는 것이 보통 맞다.
- 세 진입점이 같은 규칙을 쓴다. 드래그앤드롭도 겹치면 묻는다 — 그때는 멈춰야 할 이유가 실제로
  있고, 안 겹치는 드롭은 여전히 창 없이 지나간다.
- **이동이고 겹치면 창은 하나만 뜬다.** 이동 확인창(§4.7)과 충돌창이 잇달아 뜨면 두 번 읽고
  두 번 눌러야 하므로, 충돌창이 "원본은 사라집니다"까지 말하고 그 선택이 곧 이동 확인이 된다.
- 폴더를 합칠 때는 **안쪽 파일 하나하나에** 같은 규칙이 적용된다.
- 살아 있는 목적지가 하나도 없으면(전부 접근 불가) 엔진을 부르지 않고 그 자리에서 거절한다 —
  어차피 전부 "건너뜀"으로 돌아올 것을 실행해 보고 알려 주는 것보다 낫다.
- **예외 하나 — 온 곳과 같은 폴더에 붙여넣을 때**(Phase 8-D·8-E). 소스와 목적지가 같으면 모든
  항목이 100% 겹치므로 위 창이 주는 정보가 0 이고, 기본값 덮어쓰기는 자기를 자기로 덮는
  무의미한 동작이 된다. 그래서 **셋 중 고르게 하지 않고 「둘 다 두기」로 간다** —
  `a.txt` → `a (2).txt`. 이름 형식은 위 「둘 다 두기」가 쓰는 그것이다(따로 만들지 않았다).
  - **저장된 정책(`onConflict`·`askOnConflict`)을 따르지 않는다.** 그 정책은 다른 폴더로
    붙여넣을 때의 것이다.
  - **대신 진행/취소만 묻는 확인창이 뜬다**(Phase 8-E). 고를 것이 없으므로 충돌창이 아니라
    결과를 미리 말하는 창이다 — 무엇이 어떤 이름으로 생기는지 앞 다섯 줄을 적고 나머지는
    `… 외 N개` 로 접는다. 전부 적으면 항목이 많을 때 버튼이 화면 밖으로 나간다.
  - 판정은 **뭉치 단위**다. 클립보드의 **모든** 항목이 목적지에서 왔을 때만 이 경로다. 섞여
    있으면 기존 규칙 그대로고, 같은 폴더에서 온 것만 빠져 결과에 「온 곳과 같은 폴더 N」으로
    잡힌다. 항목마다 정책을 갈면 한 번 누른 것이 조작 둘·결과 보고 둘이 되고 뒤가 앞을 덮는다.
  - **잘라내기(이동)는 그대로 거절한다.** 같은 폴더로 옮기는 것은 아무 일도 아니다.

### 4.4 쓰레기 정리

Phase 3 Stage 3 에서 구현하며 아래로 확정했다(원래 Phase 4 항목이었다 — §9 이력 참고).

- 상위 폴더 등에서 임시/불필요 파일을 다중 선택해 한 번에 삭제. 폴더도 통째로 간다.
- 삭제는 영구 삭제가 아니라 **휴지통으로 보내기**(실수 방지).
- **확인창을 두지 않는다.** 휴지통을 고른 이유가 "되돌릴 수 있게"인데 그 앞에 확인을 또
  세우면, 임시 파일을 훑어 지우는 이 경로가 매번 막힌다(탐색기 기본값도 확인 없음).
  대신 **몇 개를 보냈는지 반드시 알린다** — "3개를 휴지통으로 보냈다 — 되돌릴 수 있다."
  하나라도 실패하면 요약이 빨강으로 상태 바에 남고 사유가 따로 뜬다(§5).
- 진입점 셋: 툴바 "휴지통으로 삭제" 버튼 / 항목 우클릭 메뉴 / `Del` 키.
  우클릭은 그 자리에서 선택을 잡아 준다(선택 밖 항목을 누르면 그것만) — 무엇이 지워질지가
  눌린 순간 목록에 보여야 하기 때문이다.
- `Shift+Del`(영구 삭제)은 탐색기와 달리 **막는다**(확인창이 아니라 거절). 되돌릴 수 없는
  동작을 실수로 부르는 자리를 아예 두지 않는다. 거절 문구는 대안을 같이 말한다.
  구현상 앱에 영구 삭제 경로 자체가 없다.
- 휴지통 호출은 `SHFileOperation` + `ALLOWUNDO`. `NOCONFIRMATION` 만 주면 휴지통에 못 넣는
  경우(용량 초과·네트워크·이동식) 셸이 **말없이 영구 삭제**하므로 `WANTNUKEWARNING` 을
  같이 준다 — 그때만 경고가 뜨고 "영구 삭제 아님"이 지켜진다.

### 4.5 파일 열기
- 파일 더블클릭 = OS 기본 프로그램으로 열기.
- **폴더 더블클릭 = 타일 안에서 하위 진입**(탐색기 동등). 탐색기 별창으로 열기는
  우클릭 메뉴 "탐색기에서 열기"로 뺀다.

### 4.6 타일 = 탐색기 뷰

#### 앵커 / 현재 경로 분리
- 타일은 `folderId`(**앵커**, JSON 저장) + `currentPath`(**런타임 전용, 저장 안 함**)를 가진다.
- 하위 진입·상위 이동 모두 자유. 앵커의 `path`는 바뀌지 않는다.
- 이유: 진입만으로 `path`가 덮어써지면 표시 이름·설명·pin 등 메타데이터가 거짓이 되고,
  상시 칸은 "못박음"이라는 존재 이유를 잃는다. 실수 클릭 하나가 워크스페이스를 영구히
  바꾸는 리스크 대비, 저장하지 않으면 최악이 "다시 들어가기" 한 번이다.
- 세션 동작: **실행 중에는 하위 경로 기억**, **앱 재시작 시 앵커로 리셋.**

#### 앵커로 돌아가는 방법 (3곳)
1. 타일 헤더 breadcrumb 첫 조각(앵커 이름) 클릭.
2. 왼쪽 리스트에서 같은 폴더 재클릭.
3. 단축키 `Alt+Home`(탐색기 "홈"과 같은 자리).

#### 현재 위치를 앵커로 승격 (명시적 액션만)
- 우클릭 "이 폴더를 앵커로 지정" — 기존 항목 `path` 교체(표시 이름 갱신 여부 물음).
- 우클릭 "새 폴더로 등록" — `folders[]`에 추가.

#### 우클릭 메뉴
- **Phase 1 = 자체 메뉴**: 열기 / 탐색기에서 열기 / 이름 바꾸기(F2) / 삭제(Del→휴지통) /
  복사(Ctrl+C) / 경로 복사 / 이 폴더를 앵커로 지정 / 새 폴더로 등록 / 속성.
  **아홉이 전부 구현됐다**(A군 ①②③ · 2026-08-18 실물 확인). **다만 위 배치는 D34 병합
  이전의 것이다.** 상시 병합 뒤 실물은 앱 항목 다섯이 **내부 구분선 없이 한 덩어리**로 먼저
  오고(탐색기에서 열기 · 이름 바꾸기 · 이 폴더를 앵커로 지정 · 새 폴더로 등록 · 휴지통으로
  삭제), **구분선 하나** 뒤로 셸이 채운다. 열기 · 복사 · 경로 복사 · 속성 넷은 앱이 넣지 않고
  셸 것을 쓴다(아래 D34). 이 절이 한때 「읽기 여섯 → 구분선 → 쓰기 둘 → 구분선 → 삭제」라
  적어 두었던 배치는 **그 넷을 앱이 넣던 시절의 화석**이었다 — 같은 절 아래 D34 와 모순인
  채로 남아 있었고 D75 B-0 조사에서 잡았다.
  「새 폴더로 등록」과 「이 폴더를 앵커로 지정」은 **폴더 항목에서만 보인다**(파일에는 뜻이 없다).
  `F2` · `Ctrl+C` · `Del` 은 라벨이 아니라 실물이고, `F2` 와 `Ctrl+C` 는 **패널 층**에 물려
  있다 — 대상이 "이 패널에서 고른 항목"이라 창 층에 물리면 어느 패널의 선택인지 가릴 수
  없다(D16).
- 영구 삭제(`Shift+Del`)는 **확인창이 아니라 거절**이다 — §4.4 가 정한다. 자체 메뉴에 영구
  삭제 항목을 두지 않는다.
- **셸 컨텍스트 메뉴**(TortoiseGit·7-Zip 등 확장 노출)는 **상시 병합(B안)이다**(D32). 폐기된
  D26 「별 진입」을 대신하는 번호다 — **폐기된 번호는 되쓰지 않는다.** 병합 1,130줄은
  `master` 에 들어가 있다(2026-08-19). 이 구현이 처음 들어갔을 때 **워크스페이스 프로세스가
  조용히 사라지는 결함**이 함께 왔다. 원인은 셸 메뉴가 아니라 확장이 망친 FPU 예외 마스크였고
  (§8), 고침이 들어간 뒤 손 확인으로 닫혔다.
  판단 근거로 남는 것: 자체 메뉴를 셸 메뉴로 **대체하는 것은 기술적으로 불가**하고
  (`verb=rename` 이 없다), **병합하면 우클릭마다 70~90ms 가 붙으며** 확장 코드를 격리할 방법이
  없다. 목적은 상시 동등성이 아니라 **확장 노출**이다. 어느 쪽으로 가든 여는 쪽에는
  **`IContextMenu2/3` 메시지 훅이 필수**다 — 없으면 확장 서브메뉴가 빈 항목으로 남는다.
  **아이콘 때문이 아니다.** (→ §11 환경 확인 필요)
- **셸이 넣은 verb 중 `delete` 하나를 지운다**(D33 · 2026-08-20 개정). `delete` 를 남기면
  「앱에 영구 삭제 경로 자체가 없다」(§4.4)가 깨진다. `cut` 도 한때 함께 지웠으나 **되살렸다** —
  근거가 「우리 붙여넣기가 이동을 거절하므로 반드시 거절되는 죽은 경로가 메뉴에 보인다」였고,
  그 문장이 스스로 적어 둔 조건(「붙여넣기가 이동을 처리하게 되면 이 근거는 사라진다」)이
  D35 로 충족됐다. **폐기가 아니라 개정이라 번호를 새로 만들지 않는다.**
  판정은 **verb 로만** 한다 — 지역화된 항목 이름(「삭제(&D)」·「잘라내기(&T)」)으로 찾으면 다른
  언어에서 깨진다. `link`(바로 가기 만들기)는 충돌이 없어 남긴다.
- **앱 항목은 셸 항목 앞에 끼우고, 앱/셸 분기는 메뉴 id 대역 하나로 가른다**(D34). 앱 항목은
  전부 `IdCmdFirst`(0x1000) **아래**이고 셸에는 그 위 대역을 주므로 겹칠 수 없다 — 돌아온 id
  하나로 갈린다. 끼우는 것은 폴더에서 **다섯** · 파일에서 **셋**이다(「이 폴더를 앵커로 지정」·
  「새 폴더로 등록」은 폴더에만 뜻이 있어 파일에는 넣지 않는다). 셸과 겹치는 넷(`open` ·
  `copy` · `copyaspath` · `properties`)은 넣지 않고 셸 것을 쓴다 — 앱 커맨드 자체는 그대로
  살아 있고 `Ctrl+C` 등이 계속 쓴다.
- 클립보드: §7의 "앱 내부 상태 처리"는 유지하되, 탐색기 동등성을 위해 `Ctrl+C`/`Ctrl+V`도
  지원한다(대상함=앱 내부 경로). **별도의 앱 클립보드와 공존하는 것이 아니라 셸 클립보드를
  그대로 쓴다** — 싣는 것은 경로 글자가 아니라 `CF_HDROP` 이고, 드래그 내보내기(§4.9)와 같은
  함수로 싣는다. 읽는 쪽도 셸 드롭과 같은 파서를 쓴다. **효과 값만 인자로 가른다** — 기본은
  복사이고 이동은 부르는 쪽이 명시한다(D36). 드래그 내보내기가 §4.9 의 「기본은 복사」를
  그대로 지키는 것이 그 때문이다.
- **붙여넣기는 클립보드가 잘라내기를 실었으면 이동한다**(D35). `Preferred DropEffect` 가
  정확히 2(Move)일 때만이고, 엔진은 드롭 경로가 쓰는 것과 같다. **확인창은 띄우지 않는다** —
  탐색기가 묻지 않고 드롭 경로도 묻지 않으며, 사용자가 `Ctrl+X`·`Ctrl+V` 로 이미 두 번 말했다.
- **`Ctrl+X` 를 넣는다**(D36). 폐기된 D20 「`Ctrl+X` 는 넣지 않는다. 우리가 이동 클립보드를
  내는 쪽은 두지 않는다」를 대신하는 번호다 — **폐기된 번호는 되쓰지 않는다.** 뒤집은 근거는
  받는 쪽(D35)이 먼저 생긴 것이다. 대상이 「이 패널에서 고른 항목」이라 `Ctrl+C` 와 같은 패널
  층이고, 고른 것이 없으면 **클립보드를 건드리지 않고 거절한다** — 빈 것으로 덮으면 아까
  복사해 둔 것이 사라진다.
  > **계측(2026-08-20 손 확인 · 탐색기 · 같은 볼륨).** 탐색기의 `Ctrl+X` 와 셸 메뉴의
  > 「잘라내기」는 둘 다 `Preferred DropEffect` 를 **2** 로 싣는다 — 앱이 이동으로 푼다.
  > 반대로 **앱이 2 를 실으면 탐색기가 이동으로 받아 원본이 사라진다.** 한 방향의 관측은
  > 반대 방향에 적용되지 않으므로 둘을 따로 쟀다.
- 진입점이 갈린다 — 「복사」는 **고른 항목**이 대상이라 항목 우클릭 메뉴에, 「붙여넣기」는
  **타일이 지금 보고 있는 폴더**(§4.9)가 대상이라 아래 「지금 보고 있는 폴더」 메뉴에 있다.

#### 「지금 보고 있는 폴더」 메뉴 (Phase 13 · D75)

- **대상이 「타일이 지금 보고 있는 폴더」인 항목은 메뉴 하나에 모으고, 그 메뉴를 두 자리에서
  연다**(D75) — **목록의 빈 곳 우클릭**과 **breadcrumb 우클릭**. 정의는 하나다. 대상이 같은
  메뉴를 둘로 나누면 항목을 더할 때마다 어느 쪽에 넣을지가 매번 갈린다. 탐색기도 폴더 배경
  메뉴는 하나다.
  - **헤더에 「앵커로 지정」 버튼을 두지 않는다.** 헤더는 한 줄이고(§3.2), 같은 대상의 메뉴가
    이미 생기는데 버튼을 또 두면 진입점이 셋이 된다.
  - **빈 곳은 고무줄(§4.8)과 자리를 다투지 않는다** — 고무줄은 좌클릭 드래그고 이 메뉴는
    우클릭이다. D75 이전에는 「고무줄이 그 자리를 쓴다」를 근거로 빈 곳 메뉴를 두지 않았고
    그 근거는 코드 주석에만 있었다. **근거가 성립하지 않아 뒤집는다.**
- 항목 **다섯**이다 — **새 폴더 만들기** · **붙여넣기**(위 D35·D36 그대로) · **경로 복사** ·
  **이 폴더를 앵커로 지정** · **새 폴더로 등록**. 배치는 **쓰기 → 구분선 → 읽기 → 구분선 →
  워크스페이스**다(D75-c) — 앞 둘은 파일 시스템을 바꾸고 뒤 둘은 **워크스페이스**를 바꾼다.
  「경로 복사」는 **옛 breadcrumb 메뉴에 이미 있던 것**이라 그대로 데려왔다. 빼면 기능 퇴행이다.
  - **새 폴더 만들기는 이름을 모달로 묻는다**(D75). 기본값은 `새 폴더` 를 §4.3 의 이름 규칙에
    태운 결과다(같은 이름이 있으면 `새 폴더 (2)`). 만들어 두고 인라인 편집으로 넘기는 탐색기
    방식은 **목록에 인라인 편집이 없어** 쓸 수 없고(`F2` 도 모달이다), 이름 없이 만들면
    사용자가 곧바로 `F2` 를 눌러 모달을 한 번 더 띄우게 된다. **한 번에 끝내는 쪽을 고른다** —
    탐색기와 체감이 다른 것은 받아들인다.
  - **이미 있는 이름을 사용자가 입력하면 거절한다**(D75-b) — 덮어쓰지도, 이름을 바꿔 만들지도
    않는다. 탐색기와 같다. 기본값이 이미 충돌을 피해 오므로 충돌은 **일부러 입력한 경우뿐**이다.
    거절 사유는 폴더 생성 함수가 문자열로 돌려주고 그대로 통지에 실린다.
  - **모달의 확인 버튼 문구는 호출부가 정한다**(D75-e). `IUserPrompt.AskName` 이 그 문구를
    인자로 받는다 — **기본값을 두지 않는다.** 두면 다음 호출부가 문구를 안 정하고도 컴파일돼
    같은 결함이 조용히 재발한다. 새 폴더는 「만들기」, 이름 바꾸기는 「바꾸기」다. 이 창은
    이름 바꾸기와 **같은 모달**이라(새로 만들지 않았다) 문구를 밖에서 넣지 않으면 새 폴더에도
    「바꾸기」가 뜬다 — 실제로 그렇게 떴고 손 확인에서 잡혔다.
  - **`Ctrl+Shift+N` 으로도 부른다**(D75-d). 탐색기 표준이다. **목록이 가득 차면 빈 곳이
    없어** 그 진입점을 쓸 수 없는데, 4×4 격자라 **가득 찬 상태가 예외가 아니라 기본**이다.
    breadcrumb 이 늘 그 자리에 있어 기능이 막히지는 않지만 마우스를 거기까지 올려야 한다.
    바인딩은 패널 층(`UserControl.InputBindings`)이다 — `Ctrl+V` 와 같은 자리, 같은 근거로
    대상이 「이 패널이 지금 보고 있는 폴더」다.
  - 만든 폴더가 목록에 나타나는 것은 **파일 시스템 감시자**가 한다(§8). 따로 재조회하지 않는다.
  - 「이 폴더를 앵커로 지정」·「새 폴더로 등록」은 **항목 우클릭에도 그대로 있다**(위 자체 메뉴).
    대상이 다르다 — 항목 쪽은 **목록에 뜬 하위 폴더**, 이 쪽은 **지금 보고 있는 폴더 자신**이다.
    지금 보고 있는 폴더는 목록의 행이 아니라 그 목록의 **컨테이너**라 행 객체로 표현되지
    않는다 — **경로 하나를 받는 진입점이 따로 필요하다.**
- **셸 배경 메뉴는 병합하지 않는다**(D75). 항목 메뉴는 부모 `IShellFolder` 의
  `GetUIObjectOf(자식 PIDL)` 로 `IContextMenu` 를 얻는데, 폴더 자신을 대상으로 하는 배경 메뉴는
  `CreateViewObject` 로 얻는 **다른 경로**다. 확장이 등록되는 자리도 다르고, D33·D34 의 id
  대역·verb 제거 규칙을 그 경로에 **다시 걸어야** 한다. 필요해지면 별도 번호로 연다.
- **검색 타일에서는 이 메뉴를 열지 않는다**(D75 · §4.12). 다섯 항목 모두 대상이 없다 — 만들
  자리도 앵커로 지정할 폴더도 없다. 판정은 `CurrentPath` 가 `null` 인 **부작용이 아니라 검색
  타일임을 직접 묻는다** — 이름에 의도가 드러난다. D69 가 「폴더 먼저」·「하위 포함」을 통째로
  숨긴 것과 같은 결이다. **죽은 손잡이를 보이는 채로 두지 않는다.**
  - **취소는 메뉴가 열리기 전 단계에서 한다**(D75-d) — `ContextMenuOpening` 에서 막는다.
    목록과 breadcrumb **두 자리 모두**다. 커맨드 안쪽 가드는 **지우지 않았다** — 이중 방어다.
    - **컬럼 머리 검사가 이 검사보다 먼저 온다**(Phase 15 · D79). 검색 타일에서도 **컬럼 선택
      메뉴는 열려야 하기 때문이다**(§3.2 — 검색 뷰도 토글된다). 검색 타일 검사가 먼저 오면
      헤더 우클릭까지 통째로 죽는다. **여기서 막는 것은 「지금 보고 있는 폴더」 메뉴뿐이다.**
  - 그래서 커맨드 안쪽 거절 문구는 메뉴로는 도달하지 않지만 **`Ctrl+Shift+N` 으로는 도달한다.**
    검색 타일에서 눌리면 그 문구가 뜬다.
- **컬럼 머리 위에서도 「지금 보고 있는 폴더」 메뉴는 열지 않는다**(D75-d). 컬럼 머리는
  「지금 보고 있는 폴더」가 아니라 **목록의 표시 방식**을 다루는 자리다 — 이미 왼쪽 클릭에
  정렬이 걸려 있고(D69-g), 그 자리는 **컬럼 선택 메뉴가 갖는다**(Phase 15 · D79 · §3.2).
  - **빈 곳/항목 판정은 `RubberBand.Classify`(§4.8)를 재사용한다** — 새 히트테스트를 만들지
    않는다. 같은 자리가 두 뜻을 가지면 안 된다.
  - **다만 `Classify` 는 컬럼 머리를 `Empty` 로 준다** — 컬럼 머리는 `ListView` 의 헤더 행
    자손이지 `ListViewItem` 자손이 아니기 때문이다. 그래서 `Classify` 를 고치지 않고
    **`GridViewColumnHeader` 조상 검사 하나를 메뉴 쪽에만 더한다.** `Classify` 를 고치면 §4.8
    고무줄이 함께 움직인다.
  - **D79 는 그 검사를 지우지 않고 뜻을 바꾼다.** 지금 그 분기는 메뉴를 **취소**한다 — Phase
    15 는 같은 분기에서 **취소하지 않고 비켜 준다.** 메뉴를 붙이는 것은 핸들러가 아니라 **두
    `GridView` 의 `ColumnHeaderContainerStyle`** 이다(§3.2) — 헤더가 자기 메뉴를 가지면 「지금
    보고 있는 폴더」 메뉴까지 거슬러 올라가지 않는다. **핸들러가 계속 취소하면 헤더 자신의
    메뉴도 함께 죽는다** — `ContextMenuOpening` 은 버블링이라 헤더에서 열릴 때도 이 핸들러가
    불린다. 바뀌는 것은 「아무것도 안 뜬다」가 「컬럼 메뉴가 뜬다」로 되는 것뿐이고, 「지금 보고
    있는 폴더」 메뉴는 여전히 안 열린다.
  - **좌클릭 정렬과 다투지 않는다**(D78 B-0). `GridViewColumnHeader.Click` 과 `ContextMenu` 는
    WPF 의 서로 다른 하위 시스템이라 같은 요소에 얹혀도 상대의 파이프라인을 건드리지 않는다.
    **런타임으로 확인한 것은 아니다** — 코드 구조로 판정했다.

### 4.7 매크로

대상함·드래그·매크로를 관통하는 **단일 실행 엔진**의 사용자 정의 규칙. Core에 엔진을 두고
세 진입점이 얹히므로, 대상함을 UI에 박아 구현하지 않는다.

정의(workspace JSON에 옵셔널 슬롯):
```
{ id, name,
  op:         copy | move | trash,
  source:     { kind: fixedPath | selection, path? },
  dest:       { kind: allVisible | tray | folderIds, folderIds? },
  onConflict: overwrite | skip | rename,
  confirm:    true }
```
- `fixedPath` + `allVisible` = "특정 경로 파일을 열려 있는 모든 폴더로 복사".
- `selection` = 지금 고른 것에 대해 한 번에.
- `pattern` 소스는 v1 제외(오폭 위험). `source.kind`에 나중에 추가.

안전장치:
- **실행 전 미리보기가 기본**: "무엇 → 어디, N건, 덮어쓸 것 M건 + 목적지별 내역".
  매크로별로 끌 수 있게 하되 기본은 켬. `move`/`trash`는 확인 강제(끄지 못함).
- `allVisible`의 정의 = **보이는 경로(`currentPath`) 기준.** 앵커가 아니라 화면에 뜬
  그대로가 대상이라 예측 가능하고, 미리보기에 경로가 전부 찍힌다.
- 접근 불가 목적지는 실행에서 제외(경로는 유지).

**Phase 3 Stage 5 에서 구현하며 정한 것.**

- **만들기는 "지금 상태를 굳히는" 것이다.** 대상함·매크로 탭의 "지금 설정으로 매크로 만들기"를
  누르면 창이 지금 고른 것·체크된 대상함·충돌 정책으로 **미리 채워져** 뜬다. 대개는 이름만 쓰고
  확인을 누르게 된다 — 방금 손으로 한 조작을 규칙으로 남기는 것이 주 용도라서. 처음부터 폼을
  채우게 하지 않는다.
- **`source.path` 는 경로 하나다**(§4.7 그대로). 그래서 "이 경로로 고정"은 **대상이 하나일 때만**
  고를 수 있고, 여럿을 고른 상태에서는 잠긴다. 대표 예 `fixedPath` + `allVisible` 이 원래
  "파일 하나를 열려 있는 모든 폴더로"라 이 제약이 걸림돌이 되지 않는다.
- **`folderIds` 는 만드는 순간에 굳는다.** 나중에 대상함 체크가 바뀌어도 그 규칙이 가리키는
  곳은 그대로다. 실행할 때의 체크를 따르고 싶으면 `tray` 를 고른다 — 둘의 차이가 창에 적혀 있다.
- **매크로는 자기 `onConflict` 를 쓴다.** §4.3 의 "겹치면 묻기"는 직접 조작(버튼·드래그)용이고
  매크로에는 적용하지 않는다. 반복 실행이 존재 이유인데 매번 물으면 자동화가 아니다. 대신
  미리보기가 "같은 이름 M건은 건너뜁니다"처럼 무엇을 할지 미리 적는다.
- **이동은 규칙이라고 예외가 아니다** — 목적지가 둘 이상으로 풀리면 거부한다(§4.2).
- 대상·목적지가 실행 시점에 비면 **엔진을 부르지 않고** 이유를 말한다("고정 경로가 사라졌다",
  "먼저 그리드에서 파일을 고른다", "목적지가 없다").
- 확인을 끈 복사 규칙은 카드에 **"확인 없이 바로 실행"**이라고 빨갛게 적어 둔다 — 누르면
  그 자리에서 파일이 움직인다는 뜻이라 눌러 보기 전에 알아야 한다.
- `macros[]` 는 v1 부터 모델에 자리가 있던 슬롯이라 **스키마 버전은 그대로 4**다(필드 추가 없음).

### 4.8 선택(selection) 규칙
- **선택 상태는 타일 하나에만 존재.** 다른 타일 클릭 시 이전 타일 선택 해제.
  매크로/대상함의 "현재 선택"이 어디를 말하는지 명확해진다.
- **목록을 다시 읽어도 고른 것은 살아남는다**(Phase 3 Stage 5). 경로로 기억했다가 새 목록의
  항목으로 다시 잡는다. 옮겨서 사라진 파일은 자연히 빠진다.
  - 이유: `Items` 를 갈아끼우면 `ListView` 가 자기 선택을 비우고 그 통지가 뷰모델까지
    지운다. 그대로 두면 **창을 잠깐 떠났다 돌아오기만 해도**(§8 활성화 재조회) 선택이
    날아간다. 매크로를 만들고 바로 실행하면 "대상이 없다"가 뜨는 것이 그 증상이었다.
  - **단, 뷰 방식을 바꾸면 살아남지 않는다** — 전환하면 선택이 비워진다(§3.2 뷰 토글).
    `list` 와 `details` 가 각자 `ListView` 를 갖고 각자 선택을 들기 때문이다. 경로로 다시
    잡아 주지 않는다 — v1 결정이다.
  - **정렬을 바꾸면 살아남는다** — 뷰 전환과 다르다. 목록을 다시 읽는 경로를 그대로 타고
    선택을 경로로 다시 잡기 때문에 `ClearSelection()` 을 부르지 않는다(§3.2 정렬 글자).
- **고무줄 선택**(Phase 5 Stage 3 단계 B·C·D). 목록의 **빈 곳**에서 버튼을 누른 채 끌면
  사각형이 그려지고 걸친 항목이 선택된다.
  - **빈 곳과 항목의 경계는 히트테스트가 가른다.** 마지막 항목 아래 여백과 컬럼 오른쪽
    여백은 빈 곳이고, **행의 내용 폭 안은 어디든 그 행**이다 — 셀 안 좌표는 계산하지 않는다.
    세로 스크롤바 위는 둘 다 아니어서 고무줄이 시작되지 않는다.
  - **컬럼 머리에서는 실물에서 아무 일도 일어나지 않는다**(D78 B-0 · 손 확인 2026-09-02).
    `Classify` 가 컬럼 머리를 `Empty` 로 주므로(§4.6) **코드상으로는 시작 조건이 성립하는데**,
    실제로 누르고 끌면 사각형이 그려지지 않고 선택도 늘지 않는다. 컬럼 폭 끌기는 정상이다.
    **가드를 넣지 않는다** — 없는 결함에 가드를 넣으면 바로 위의 「경계는 히트테스트가
    가른다」에 예외 조항이 하나 는다.
    - **기전은 재지 않았다.** 컬럼 머리가 마우스 캡처를 스스로 가져가는 것으로 보이나 관측은
      「누르고 끌면 아무 일도 없다」 하나뿐이다. **컬럼 머리 템플릿을 건드리는 회차는 이
      관측을 무효로 보고 손 확인을 다시 내라.**
  - **시작할 자리는 컬럼 폭 계산이 일부러 남긴다** — 꽉 맞추면 고무줄이 죽는다. 상세 뷰에서
    그 자리는 **항상 오른쪽 32px** 이다(타일 폭이 463px 이상일 때). 463px 아래에서는 가로
    스크롤이 남아 **아래 여백만** 시작 자리다. 판정에 필요한 폭은 **4px** 이고 32px 는 손으로
    집을 폭으로 **정한 값**이다 — 관측이 아니다.
    32px 와 463px 이 어디서 나오는지는 **§3.2 「컬럼 폭 자동 조절」**이 갖는다.
  - **`Ctrl` 을 누르고 끌면 기존 선택에 더한다**(누르지 않으면 갈아치운다). **수정키는 끌기를
    시작하는 순간에 판정한다 — §4.2-2 의 드롭(놓는 순간)과 반대다.** 사각형을 그리는 동안
    무엇이 잡힐지가 눈에 보이므로 도중에 뜻이 바뀌면 안 된다.
  - **맞닿기는 겹침이 아니다.** 사각형의 변이 항목의 변에 닿기만 하면 고르지 않는다.
  - **`Esc` 로 취소하지 않는다.** 버튼을 떼는 것과 구별되는 동작이 없다 — 뗀 자리에서 끝난다.
    `Esc` 에 남은 값은 마우스 캡처가 어떤 이유로 안 풀렸을 때의 **안전망 하나**다.
  - **v1 에서 빼는 것**: `Shift`+고무줄 · 사각형이 목록 끝에 닿았을 때의 **자동 스크롤** ·
    **`Esc` 로 이전 선택 복구**. 셋 다 고무줄 자체가 아니라 그 위에 얹는 편의고, `Ctrl`
    더하기와 "스크롤한 뒤 다시 끌기"로 대체된다.
  - **배치 편집 중에는 저절로 막힌다** — 그 모드에서 패널이 통째로 히트테스트를 받지 않는다(§3.2).
- **선택 강조는 포커스가 있든 없든 같은 색이다.** 기본 `ListViewItem` 은 포커스가 없으면 거의
  흰색으로 그리는데, 마우스 캡처는 포커스를 옮기지 않아서 고무줄로 고르면 아무 표시가 안 보였다.
  전용 토큰 `Brush.SelectionSurface` 를 두어 두 상태를 같은 색으로 묶었다 — 색값은
  `doc/FolderDeck_familylook_spec.md` §4 가 갖는다.

### 4.9 외부 드래그앤드롭 (셸 연동) — Phase 5

Phase 4 착수 논의에서 추가했다. §4.2-2 의 드래그가 끝나는 「앱 안」은 실은 **같은 프로세스
안**이다(다른 타일·폴더 리스트·대상함). 워크스페이스마다 프로세스가 따로이므로(§6.2) **다른
FolderDeck 창은 이 앱이면서 프로세스가 다르다** — 갈래는 둘이 아니라 셋이다. 셋째 갈래를
어떻게 처리하는지는 아래 「받는 쪽의 순서」에 적었다(Phase 14).
타일이 탐색기 뷰라는 것(§4.6)이 진짜면 앱 경계에서 드래그가 멈출 이유가 없다. 양방향 다 넣되
성격이 달라 규칙도 다르다. 셸 interop 영역이므로 Phase 5 로 묶는다(§9).

#### 받기 (밖 → 타일) — 엔진의 네 번째 진입점

- 탐색기·바탕화면 등에서 끌어온 파일·폴더를 타일에 놓으면 `IFileOperationEngine` 이 처리한다.
  **엔진은 그대로 재사용된다** — 충돌 정책(§4.3)·부분 실패 보고(§5)·진행·취소(§1.1)가 전부
  다시 쓰이고, 셸이 주는 경로 목록이 엔진 인자로 변환 없이 들어간다. **Stage 1 에서 실제로
  돌려 확인했다** — 엔진 계약을 바꾸지 않았고 변환 계층도 만들지 않았다.
  **비용은 엔진이 아니라 UI 에 있었다** — 타일(파일 목록 패널)에 드롭 과녁이 없어서 Stage 1
  이 새로 만들었다(`AllowDrop` 이 걸린 자리가 넷 → 다섯). 「진입점이 하나 늘 뿐」이라고 적었던
  것이 값을 낮춰 적은 것이었다.
  **타일 과녁은 밖에서 온 것과 앱 안에서 온 것을 다 받는다**(Phase 5 Stage 3 단계 A). Stage 1
  이 만든 과녁은 셸 드롭만 받았고 내부 드래그(§4.2-2)는 타일에서 **시작**만 했다 — 단계 A 가
  그 비대칭을 없앴다. 타일↔타일 드롭은 §4.2-2 의 규칙(**볼륨이 가르고 수정키가 이긴다**)으로
  처리된다. 한 드롭에 두 포맷이 다 실렸을 때 어느 규칙으로 처리하는지는 아래
  「받는 쪽의 순서」가 정한다.
- **놓이는 곳은 타일의 `currentPath`**, 앵커가 아니다. §4.7 `allVisible` 과 같은 기준이라
  "화면에 보이는 그대로가 목적지"로 일관된다.
- **기본 복사, `Shift` 를 누르면 이동.** §4.2-2 의 앱 내부 규칙과 **일부러 다르다** — 앱 안은
  볼륨이 가르지만 밖에서 오는 것은 **볼륨과 무관하게** 복사가 기본이다.
  앱 안의 드래그는 이미 이 워크스페이스에 속한 파일을 옮기는 것이라 같은 볼륨이면 이동이지만,
  밖에서 들어오는 것은 남의 폴더에 있는 원본이다. 확인창이 없는 경로(§4.2-2)에서 기본값이
  이동이면, 한 번의 드래그가 앱이 관리하지 않는 폴더의 파일을 지운다.
- 확인창은 §4.2-2 와 같이 **없다.** 겹치면 §4.3 이 그대로 뜬다(안 겹치면 조용히 지나간다).
- 왼쪽 폴더 리스트 항목과 대상함도 함께 받는다 — 내부 드래그가 받는 자리와 같게 둔다.
- 받지 않는 조합은 §4.2-2 의 ②(폴더를 자기 자신이나 자기 하위로)·③(다른 조작이 도는 중)이
  그대로다. **①(온 곳과 같은 폴더)만 판정 단위가 다르다 — 뭉치가 아니라 항목마다 본다.**
  앱 안의 드래그는 뭉치의 출처가 패널 하나여서(§4.8) 한 번만 보면 됐지만, 셸 드롭에는 그
  전제가 없다(탐색기 검색 결과처럼 서로 다른 폴더의 항목이 한 번에 온다). 그래서 온 곳이
  목적지와 같은 **그 항목만** 건너뛰고 나머지는 처리하며, 건너뛴 건수는 결과에 적는다(§5).
  **과녁은 하나라도 받을 수 있으면 켠다** — 전부 같은 폴더일 때만 켜지 않는다.
  건너뛴 건수는 §5.1 의 **남는** 등급으로 알린다(조용히 사라지면 무엇이 안 갔는지 모른다).
  다만 **사유 목록 창은 열지 않는다** — 이 경로는 확인창을 두지 않기로 한 자리다(§4.2-2).
  엔진이 돌려준 건너뜀·실패는 지금처럼 그대로 보고된다(§5).

#### 내보내기 (타일 → 밖) — 기본은 복사

- 타일 항목을 앱 밖으로 끌면 탐색기 창·브라우저 업로드칸 등이 받는다. 파일 경로 목록을 싣는
  표준 셸 드래그이며, 대상이 실제 디스크 파일이라 가상 파일 처리는 필요 없다. 폴더도 끌 수 있다.
  **폴더는 받는 쪽에 따라 다르게 풀린다**(Stage 0 실측): 탐색기는 폴더를 폴더로 받고,
  브라우저 업로드칸은 폴더가 아니라 **그 안의 파일**을 받는다. 앱이 정하는 것이 아니라
  목적지가 정하는 것이라 규칙으로 못박지 않고 사실만 적어 둔다.
- **기본은 복사이고, 앱이 이동을 고르지 않는다.** `DataObject` 에 `Preferred DropEffect` 를
  `DROPEFFECT_COPY` 로 실어 셸이 기본으로 복사를 고르게 못박는다. `allowedEffects` 는
  `Copy | Move` 그대로 둔다(내부 드래그의 이동이 같은 `DoDragDrop` 호출을 쓴다 — §4.2-2).
  **다만 사용자가 `Shift` 를 누르면 셸이 이동하고, 앱은 그것을 막지 않는다.** 이 앱은 탐색기의
  덱이라 표준 제스처를 가로채지 않는다. 판정 주체가 목적지가 아니라 **사용자**이므로
  "앱이 판정하지 않았는데 원본이 사라지는" 조합이 아니다.
  > **이 문단은 Phase 5 Stage 2 의 계측으로 뒤집혔다.** 원래는 "복사만 제공한다. 이동은 넣지
  > 않는다"였고 근거는 이동/복사 판정을 목적지가 한다는 것이었다. `Preferred DropEffect` 로
  > 기본을 못박을 수 있다는 것을 몰라 통째로 막는 수밖에 없었던 문장이다.
  > 계측(같은 볼륨·탐색기): PDE 없으면 `DoDragDrop = Move` 로 **원본이 사라진다**.
  > PDE=`COPY` 면 `Copy` 로 원본이 남는다. PDE 가 있어도 **`Shift` 를 누르면 `Move`** 다.
- **§4.2-2 의 "결과를 상태 바에 반드시 적는다"가 이 경로에는 적용되지 않는다.** 복사를 셸이
  하므로 성패를 앱이 알 수 없다. 예외임을 여기 적어 둔다 — 넘겼다는 사실까지만 알린다.
  **`Shift` 이동일 때도 마찬가지다** — 원본이 사라지는데도 앱은 그 결과를 모른다. 복사보다
  값이 큰 예외다. 그래서 문구는 "복사했다"가 아니라 **"넘겼다"** 로 쓴다 — 앱이 모르는 것을
  안다고 말하지 않는다.
- **이 알림은 앱 안에 놓았을 때는 뜨지 않는다.** `DoDragDrop` 의 반환값은 어디에 놓였는지
  말하지 않으므로(앱 안 폴더 행에 놓아도 `Copy`/`Move` 가 돌아온다) 반환값만 보고 적으면
  내부 드롭의 결과를 덮어 §4.2-2 를 어긴다. 그래서 **끄는 쪽이** 드래그 한 번 동안만 창의
  `PreviewDrop` 을 보고 앱 안 드롭을 가린다 — **받는 쪽 코드는 건드리지 않는다**(§4.9 의
  받기 규칙과 §4.2-2 의 내부 규칙이 서로를 모른 채로 남는다).
- 진행줄·취소(§1.1)도 앱 것이 아니라 셸의 진행창이다. 일관성은 깨지지만 대안이 없다.
- **시작 제스처는 갈리지 않는다**(Stage 0 확인). 내부 드래그도 이미 `DoDragDrop` 이고,
  "내부"와 "셸"의 차이는 `DataObject` 에 실은 포맷뿐이다. 한 드래그에 사설 포맷과 셸 포맷을
  함께 실으면 사설 포맷을 아는 쪽은 그것을, 모르는 쪽은 셸 포맷을 읽는다 — 두 포맷을 함께
  실은 드래그를 탐색기가 실제로 받는 것까지 확인했다. **갈림은 시작이 아니라 받는 쪽에서
  일어난다.** **「사설 포맷을 아는 쪽」은 같은 프로세스만이 아니다** — 다른 FolderDeck 창도
  같은 포맷 이름을 안다(§6.2). 받는 쪽이 구분해야 하는 것은 셋이다: 같은 프로세스 · 다른
  FolderDeck 프로세스 · 남의 앱. 앞의 둘은 사설 포맷을 읽어 §4.2-2 규칙으로, 마지막 하나는
  셸 포맷을 읽어 이 절의 받기 규칙으로 처리한다.
  드래그가 앱 밖을 다녀와 다시 들어와도 과녁 강조가 다시 켜진다(실측).
- **받는 쪽의 순서를 정했다**(Phase 5 Stage 1). 한 드롭에 두 포맷이 다 실려 있으면 **사설
  포맷을 먼저 보고 그 자리에서 끝낸다** — 내부 규칙(볼륨이 가른다 · §4.2-2)으로 처리하고 셸
  분기로 내려가지 않는다. 사설 포맷이 없을 때만 셸 포맷을 본다(기본 복사/`Shift` 이동 —
  일부러 다르다). 두 분기가 같은 드롭을 둘 다 물어 **두 번 처리되는 것**을 이 순서 하나로 막는다.
  - **사설 포맷이 실려 있는데 실물을 못 꺼내면 셸 분기로 내려가지 않고 거절한다.** 포맷이
    있다는 것만으로 내부 갈래가 확정되고, 그 안에서 실패하면 받지 않는다 — 과녁이 안 켜지고
    커서는 「안 됨」이다. **이것은 의도한 것이다**: 못 꺼낸 실물을 셸 포맷으로 대신 읽으면
    같은 드래그가 규칙이 달라져(이동이 복사가 되어) 조용히 다른 일을 한다.
  - **그래서 사설 포맷에는 객체가 아니라 직렬화된 글자를 싣는다**(Phase 14). 프로세스 경계를
    넘을 때 객체는 마샬링되지 않아 「있는데 못 꺼내는」 상태가 되고, 위 규칙에 따라 다른
    FolderDeck 창으로 끄는 것이 **통째로 거절됐다.** 글자는 경계를 넘는다 — 받는 쪽이 그것을
    풀어 §4.2-2 규칙으로 처리하므로 **창이 하나든 둘이든 같은 규칙이다.**
    > **실패 기전 자체는 확정하지 않았다.** 마샬링이 어느 경로에서 어떻게 실패하는지는
    > 재지 않았다 — 재지 않아도 고칠 수 있는 자리라 재지 않기로 했다(Phase 14 D76).
    > **고친 뒤 손으로 확인했다**(2026-09-02 · 서로 다른 워크스페이스 창 둘): 같은 볼륨
    > 이동 · `Ctrl` 복사 · 같은 창 안 회귀 **셋 다 통과.** 기전은 여전히 모르고 결과만 안다.
  - 순서는 **한 곳에 두고 받는 세 자리가 같이 쓴다.** 세 군데에 같은 판정을 베껴 쓰면
    하나만 고쳐지는 사고가 난다.
  - `DragOver` 와 `Drop` 이 **같은 순서를 본다.** 한쪽만 보면 과녁은 켜지는데 처리되지
    않거나 그 반대가 된다.
  - **두 포맷이 함께 실린 드롭을 실제로 떨어뜨려 확인했다**(Phase 5 Stage 2). 내보내기가
    만든 실물 `DataObject` 를 실제 OLE 경로로 받는 세 자리에 떨어뜨렸다 — 폴더 행과 대상함이
    **사설 포맷 규칙으로 정확히 한 번씩** 처리하고(기본 이동 / `Ctrl` 복사 그대로), 타일은
    사설 포맷을 받지 않으므로 받지 않았다. 두 번 처리되는 경우는 없었다.
    > **이 마지막 문장은 Stage 2 시점의 관측이다.** Phase 5 Stage 3 단계 A 가 타일에도 내부
    > 드롭을 열었으므로 지금 타일은 받는다. 계측 기록으로만 읽어라.

### 4.10 파일 목록 검색

**구현은 Phase 1 부터 있었고 문서에만 없었다** — Phase 5 Stage 1 손 확인 중에 드러났다
(§3.1 런처의 폴더 드롭과 같은 종류의 누락이다). 지금 동작을 사실대로 적어 둔다.

- 맞추는 방식은 **이름의 부분 일치, 대소문자 무시**다. 비재귀·재귀 두 경로가 같은 규칙을 쓴다.
  **와일드카드(`*`·`?`)를 해석하지 않는다** — `*` 는 글자 그대로 찾는다.
- **하위 폴더까지 포함하는 검색이 있다.** 그 결과 목록은 **서로 다른 폴더의 항목이 섞인다** —
  타일 하나의 목록이 한 폴더의 내용이라는 전제가 이때만 깨진다.
- **검색은 읽기 전용이 아니다.** 검색 결과를 끌면 파일이 실제로 움직이고(§4.2-2), 그때 ①의
  판정이 항목 단위로 돌아 하위 폴더의 항목이 목적지로 모인다. **검색이 무엇을 고르느냐가
  곧 무엇이 움직이느냐다.**
- **이름만 보므로 폴더도 걸린다.** 폴더 이름이 질의에 맞으면 폴더가 결과에 들어가고, 그것을
  끌면 **폴더가 통째로 움직인다**(재귀·진행·취소 — §1.1). 그래서 위 항목의 위험은 파일 몇
  개가 아니라 **트리 하나만큼** 커질 수 있다. 와일드카드를 정할 때 이것이 오폭 논의의 실제
  크기다.
- ~~매칭 규칙을 무엇으로 할지는 아직 정하지 않았다.~~ — **Phase 12 · D69 에서 정했다.
  부분 일치 그대로 둔다.** 와일드카드를 여기에 넣지 않는 근거가 생겼다: **전역 검색 타일
  (§4.12)이 와일드카드를 갖는다.** Everything 질의는 `*`·`?` 를 해석하고 **그것을 끄는 수단이
  API 에 없다.** 두 검색이 같은 글자를 다르게 읽는 것은 피할 수 없으니, **상자를 갈라 규칙이
  다르다는 것을 눈에 보이게 한다.** 한 상자에 두 규칙을 얹으면 사용자가 자기가 친 `*` 가
  무엇으로 읽히는지 알 방법이 없고, 위의 세 번째·네 번째 항목 때문에 **그 차이가 곧 무엇이
  움직이는가의 차이**가 된다.
- 매크로 `source.kind` 의 `pattern` 을 v1 에서 뺀 이유였던 **오폭 위험**(§4.7)은 사라지지
  않는다. **§4.12 로 옮겨 갈 뿐이고 거기서는 결과 상한으로 다르게 막는다.**
  

### 4.11 폴더 등록·제거·수정

워크스페이스의 `folders[]` 를 **앱을 켠 채로** 늘리고 줄이고 고치는 경로다. 지금까지
폴더가 생기는 자리는 런처에서 워크스페이스를 통째로 만들 때 하나뿐이었고, 앱 안에는
추가도 제거도 없었다. 등록한 폴더를 잘못 골랐으면 워크스페이스를 다시 만드는 수밖에
없었다는 뜻이다.

**진입점은 왼쪽 폴더 리스트다.** 「대상함에 추가」·「순환 칸 지정」이 이미 있는 우클릭 메뉴에
「제거」·「수정」이 그 아래 붙는다. **자주 쓰는 둘은 눈에 보이는 자리에도 낸다**(D38) — 목록
헤더의 「＋」가 등록, 행의 「✕」가 제거다. 메뉴에만 두면 폴더를 앱 안에서 늘리고 줄일 수
있다는 것 자체를 모르는 채로 쓰게 된다. **등록은 자리가 하나 더 있다** — 타일 파일 목록에서
폴더 항목을 우클릭했을 때의 「새 폴더로 등록」이다. **하위 폴더까지 포함해 검색한 결과에서도
똑같이 뜬다**(§4.10) — 그 목록은 여러 폴더의 항목이 섞인 것이라 오히려 등록하고 싶은 폴더를
만나기 쉬운 자리다.

**1. 등록**
- 경로 정규화와 잎 이름 뽑기는 **Core 한 곳**에만 둔다. 등록·드롭·런처가 각자 갖게 되면 세
  곳의 규칙이 조용히 갈라진다.
- `displayName` 기본값은 경로의 잎 이름, `description` 은 빈 값으로 시작한다.
- **같은 `path` 가 이미 있으면 거절하고 이유를 말한다. 다만 거절은 UI 층에서만 한다** — 파일을
  여는 시점의 검증에는 넣지 않는다. json 을 손으로 고치다 경로가 겹친 사용자가 워크스페이스
  자체를 못 열게 되는 쪽이 더 나쁘다.
- **넣는 자리가 둘이다.** 저장되는 `folders[]` 와 왼쪽 리스트가 읽는 화면 쪽 목록은 워크스페이스를
  열 때 한 번 맞춰질 뿐 **그 뒤로는 서로를 따라가지 않는다**. 등록·제거는 반드시 둘 다에
  반영하고 저장까지 부른다.
- 저장은 다른 변경과 같은 공용 경로를 타므로 **디바운스가 그대로 걸린다**(§5).
- **폴더 고르기 대화상자는 창이 들고 있다**(D38). 뷰모델 생성자는 열 인자 그대로다 — 붙여넣기
  회차가 박아 둔 못(§8 정지 조건 2)을 이번 편의로 뽑지 않는다. 대신 「＋」를 눌러 대화상자가
  열리고 고른 결과가 등록까지 이어지는지는 **시험이 물지 못한다** — 손 확인으로만 잡힌다.

**2. 제거**
- **확인창이 딸려 갈 것을 미리 센다** — 「이 폴더를 쓰는 타일 N개·대상함 M개·매크로 K개가 같이
  정리된다」. 폴더 하나가 화면 배치와 저장된 규칙 여러 곳에 동시에 걸려 있어서, 세어 보이지
  않으면 무엇이 사라지는지 누르기 전에 알 방법이 없다.
- 여기서 **고아 참조**란 가리키던 폴더가 없어져 버린 `folderId` 를 말한다. **지금은 셋의 처리가
  제각각이다** — 타일은 세어서 알리고 그 결과를 저장까지 하고, 대상함은 조용히 흘리면서 파일에서도
  지우고, 매크로는 정의에 죽은 id 를 남긴 채 실행할 때만 거른다. **제거 경로는 셋을 같은 규칙으로
  맞춘다: 세어서 보이고, 지우고, 저장한다.** **매크로 정의에 남은 죽은 id 도 이때 함께 지운다.**
- **폴더가 사라졌거나 접근 불가인 것과는 다르다.** 그쪽은 목록에서 지우지 않고 상태로만
  남긴다(§5) — 네트워크 경로가 돌아오면 다시 조회돼야 하기 때문이다. **사용자가 「제거」를 누른
  것만 목록에서 없어진다.** 둘을 가르는 새 필드는 필요 없다. 접근 불가는 런타임 상태라 파일에
  흔적을 남기지 않으므로, 파일에서 사라졌다는 사실 자체가 사용자 삭제다.
- **행의 「✕」는 그 행을 가리키거나 초점이 갔을 때만 나타난다**(D38). 모든 행에 늘 띄우면 좁은
  왼쪽 컬럼에서 이름·경로·배지와 자리를 다투고, 열 줄짜리 목록이 지우는 버튼 열 개로 보인다.
- **배치 편집 중에는 「✕」가 아예 뜨지 않는다**(D39). 그때 왼쪽 목록의 행은 타일로 끌어다 놓는
  물건이지 지우는 물건이 아니다. 실물에서도 둘이 어긋났다 — 드래그가 마우스를 캡처해 커서가
  행을 떠나도 「✕」가 한동안 남고, `PreviewMouseMove` 가 터널링이라 「✕」를 잡아 끌면 행 드래그가
  시작된다. **표시 조건 하나로 둘 다 닫힌다** — 편집 중에 「✕」를 눌러 무엇이 되게 만드는 것보다
  그 자리에서 치우는 쪽이 뜻에 맞다.
- **「✕」는 중립색이다.** 위험을 말하는 일은 확인창이 맡는다 — 무엇이 같이 정리되는지 세어
  보이는 쪽이 빨간 글리프보다 정확하다. 글리프에는 문구가 없으므로 **말은 툴팁과 확인창이
  진다**: 「작업 관리에서 등록만 지운다. 실제 폴더는 그대로다」.
- **「✕」가 행 버튼의 기하를 줄이지 않는다.** 그 버튼에 클릭·우클릭·파일 드롭·배치 편집
  드래그가 전부 걸려 있어서, 오른쪽을 잘라 「✕」에 내주면 그만큼이 죽은 띠가 된다. 겹쳐 놓는다.
- **누르면 위의 제거 경로를 그대로 지난다.** 확인창도 고아 참조 정리도 같다 — 「✕」는 같은
  일을 하는 다른 손잡이일 뿐이다.

**3. 수정**
- 고치는 것은 **`displayName` 과 `description` 둘**이다. `description` 은 스키마에도 모델에도
  표시 자리에도 있었지만 **값이 들어간 적이 한 번도 없다** — 여기가 그 필드에 값을 넣는 첫 경로다.
- **`pinned` 은 수정 대상이 아니다.** 상시 칸이냐 순환 칸이냐는 타일 상태에서 유도되므로, 폴더
  쪽에서도 고칠 수 있게 하면 같은 사실을 두 곳에서 쓰게 되고 어긋날 때 어느 쪽이 옳은지 정할
  근거가 없다. 성격을 바꾸려면 타일에서 바꾼다(§2.3).
- `viewMode`·`sortBy`·`sortDesc`·`rotationSlot` 은 각자의 기존 진입점을 그대로 쓴다(§3.2·§11).

**4. 두 팝업이 같이 움직인다**
왼쪽 폴더 리스트와 빈 타일의 「이 칸에 넣을 폴더」 팝업은 **같은 목록을 본다.** 폴더를 지우면
두 곳에서 동시에 사라지고, 등록하면 두 곳에 동시에 생긴다. 의도한 동작이다 — 한쪽에만 남으면
이미 없는 폴더를 칸에 넣을 수 있게 된다.

**5. 스키마**
`schemaVersion` 은 **올리지 않는다**. 기존 필드만 쓰고 새 슬롯을 만들지 않는다(§7.1).

### 4.12 전역 검색 타일 (Phase 12 · D69)

PC 전체를 뒤지는 검색이다. 폴더 안을 보는 §4.10 과 **범위도 규칙도 다르다.** voidtools
Everything 의 색인을 쓰고 **앱이 스스로 디스크를 훑지 않는다.**

**1. 타일이다**
- 빈 칸에 넣고 뺀다(§3.2). **안 넣으면 `Everything64.dll` 을 한 번도 부르지 않는다.**
- 상시 칸의 성질만 갖는다 — 놓은 자리에 못박히고 순환이 되지 않는다(§2.3).
- **워크스페이스에 하나만 둔다.** 근거는 취향이 아니라 API 다(아래 3).

**2. 결과는 파일 목록이다**
- 항목은 폴더 타일과 **같은 뷰모델**을 쓴다. 그래서 셸 아이콘 3단(§3.2)·선택 규칙(§4.8)·
  드래그(§4.2)가 **그대로 따라온다.** 새로 배선하지 않는다.
- 표시는 **§3.2 의 검색 결과 뷰**(`이름`·`위치`·`크기`·`수정`)를 그대로 쓴다. 서로 다른
  폴더의 항목이 섞이므로 `위치` 열이 있어야 한다 — §4.10 재귀 검색과 같은 사정이다.
- **읽기 전용이 아니다.** 끌면 파일이 실제로 움직인다. §4.10 의 세 번째·네 번째 항목이
  그대로 적용되고, **범위가 PC 전체라 오폭의 크기가 더 크다.**
- **끌어낸 뭉치에 「출처 폴더」가 하나로 정해지지 않는다**(D69-f). 결과가 여러 볼륨에서
  섞여 오기 때문이다. **이동/복사 판정은 안 깨진다** — 그 판정은 이미 **항목마다** 하고
  뭉치의 출처는 문구·진단만 읽는다(`FileDropPayload.SourceFolder` 주석). 검색 타일에서는
  그 자리에 **끌린 첫 항목의 부모 폴더**를 넣는다. 여러 폴더가 섞였을 때 그 값이 뭉치
  전체를 대표하지 않는다는 것은 **알고 받아들인 한계**다.

**3. API 가 강제하는 것** (`Everything-SDK/include/Everything.h` 실물 확인 · 2026-08-31)
- **핸들이 없다.** 검색 조건도 결과도 프로세스에 하나뿐이라 두 곳이 동시에 검색하면 서로를
  덮는다. 그래서 **호출을 전용 스레드 하나에 직렬화**하고 **타일도 하나만** 둔다. 검색 상태가
  스레드 로컬인지 프로세스 전역인지는 헤더가 말하지 않는다 — **어느 쪽이든 직렬화가 옳다.**
- **`Everything_QueryW(TRUE)` 로 블로킹 호출한다.** 답장 창(`SetReplyWindow`·`IsQueryReply`)
  방식을 쓰지 않는다 — `HWND` 와 메시지 펌프 배관이 필요하고, 셸 훅(§4.6)이 이미 진 위험을
  하나 더 여는 일이다. **전용 스레드가 막혀도 UI 는 굳지 않는다.**
  - **대가**: 도는 질의를 끊는 API 가 없다. 취소는 **결과를 버리는 것**으로만 된다.
- **결과 필드는 미리 요청해야 나온다**(`Everything_SetRequestFlags`). 안 켠 필드를 읽으면
  오류로 떨어진다. 켜는 것은 **넷** — 전체 경로 · 크기 · 수정일 · 속성. 검색 결과 뷰가
  요구하는 것이 정확히 이 넷이다.
- **결과 문자열은 DLL 안쪽 버퍼를 가리킨다.** 다음 질의나 초기화가 무효화하므로 **받는 즉시
  복사한다.**
- **셸 확장과 같은 위험 범주다** — 남의 DLL 을 in-proc 로 올린다. 호출을 `FpuGuard` 로
  감싼다(§8). **오염을 실측한 적은 없다** — 비용이 거의 없어 재기 전에 거는 쪽을 택했다.

**4. 상한**
- `Everything_SetMax` 로 **기본 1000** 을 건다. `*.jpg` 한 방에 수십만이 걸리고, 그만큼 항목
  뷰모델이 생기면 **셸 아이콘 취득이 줄줄이 따라 붙는다.**
- **잘렸으면 잘렸다고 적는다** — `Everything_GetTotResults()` 가 잘리기 전 총계를 준다.
  「N개 중 1000개」. 적지 않으면 목록이 **조용히 거짓말을 한다.**
- 고르는 값은 **`200 / 500 / 1000 / 2000 / 5000`**, 기본 **1000**. 설정에서 고른다(§3.3·§7.2).

**5. 정렬은 Everything 이 한다**
- `Everything_SetSort` 에 넘기고 **받아 온 것을 다시 정렬하지 않는다.** 1000개를 받아 우리가
  다시 정렬하면 **상한 밖에 있던 항목이 빠진 채로 정렬**돼 표시가 거짓말이 된다 — §3.2 가
  재귀 검색 중 정렬을 잠근 것과 같은 결이다.
- SDK 정렬 상수가 이름·경로·크기·수정일의 오름/내림을 **모두 덮는다.**
- **컬럼 머리를 누르면 질의를 다시 던진다**(D69-f · 실제로 먹게 된 것은 D69-g). 그것이
  상한 밖까지 반영된 정렬을 받는 유일한 길이다. 색인 조회라 체감은 즉시다.
  - **누르는 열은 셋이다 — `이름`·`크기`·`수정`.** `위치` 는 **누를 수 없다.** 컬럼에 붙는
    표지가 `SortBy` 열거자인데 거기에 경로 값이 없고, 값을 더하면 워크스페이스의 `sortBy`
    문자열이 함께 움직인다(§7.1). 헤더 메타 메뉴에도 경로가 없어 넣으면 **컬럼으로만 되고
    메뉴로는 안 되는 유일한 기준**이 생긴다. Everything 에는 `SORT_PATH` 가 있으니 **못 하는
    것이 아니라 안 한 것**이다(§11).
  - **이 컬럼 뷰를 재귀 검색(§4.10)과 나눠 쓴다.** 재귀 검색 결과는 찾은 순서 그대로라
    정렬돼 있지 않다 — **거기서는 머리를 눌러도 안 먹고 화살표도 안 뜬다.** 같은 뷰가
    한쪽에서만 정렬되므로 화살표를 다는 판정이 두 상태를 갈라야 한다.
- **정렬 상태를 폴더 타일과 다른 자리에 든다.** 폴더 타일은 `FolderEntry.SortBy`/`SortDesc`
  에 저장하는데 **검색 타일에는 `Entry` 가 없다.** 패널이 스스로 들고 **저장하지 않는다** —
  질의 문자열을 저장하지 않는 것과 같은 이유다(7).

**6. 본체가 없거나 색인이 안 올라왔을 때**
- 판정은 **다섯 갈래**다: DLL 없음 · **판이 낡음** · 본체 안 떠 있음 · **색인 미적재** · 정상.
  지금 판정에는 뒤의 둘이 없어 **양쪽 다 「돌고 있음」으로 읽는다**(오류 코드 하나만 본다).
  - **색인 미적재** — `Everything_IsDBLoaded()` 로 가른다.
  - **판이 낡음** — 질의에 쓰는 `SetSort`·`SetRequestFlags`·`IsDBLoaded` 가 전부 **1.4.1
    이후**에 들어온 함수다(헤더 주석). 그보다 낡은 판이면 그 함수들이 아예 없어 부르는
    순간 터진다. **버전 숫자로 미리 가른다** — 프로브가 이미 major·minor·revision 을
    읽고 있으므로 새 native 호출이 필요 없다.
  - 사용자가 할 일이 다르므로 가른다 — 「설치를 확인하세요」와 「Everything 을 켜세요」와
    「Everything 을 새 판으로 올리세요」는 서로 다른 말이다(D65 결정 7 과 같은 결).
- **정상이 아니면 검색하지 않고 그 사실을 타일에 적는다.** 빈 목록을 보여 주면 「없다」와
  「못 찾았다」가 구분되지 않는다.

**7. 저장하는 것과 안 하는 것**
- 저장: **타일이 검색 타일이라는 사실과 배치뿐**(§7.1 v7).
- 저장 안 함: **질의 문자열과 결과.** 앱을 다시 켜면 빈 검색 타일로 뜬다. 결과는 색인 시점의
  스냅숏이라 되살리면 **이미 없는 파일을 끌 수 있게 된다.**

## 5. 저장 & 실패 처리

- **변경 즉시 저장(디바운스 400ms).** 종료 시에만 쓰면 크래시로 날아간다.
  마지막 변경으로부터 400ms 뒤에 한 번 쓴다. 워크스페이스를 새로 만들 때만 즉시 쓴다.
- 쓰기는 **임시파일 → 교체(atomic replace)**. 쓰는 중 죽어도 JSON이 깨지지 않는다.
- **JSON 손상 시 조용히 초기화하지 않는다.** 실패를 드러내고 사용자가 결정하게 한다.
- **등록 폴더가 사라졌거나 접근 불가면 목록에서 지우지 않는다.** "접근 불가" 상태로
  남긴다(네트워크 경로가 복구되면 다시 조회됨).
- 파일 조작은 **부분 실패가 기본**(설비가 쓰는 중인 로그는 잠김 등). 다중 파일 × 다중
  폴더면 "12개 중 10개 성공"이 흔하다. 결과 보고는 **성공 / 건너뜀 / 실패 + 이유**로(→ Phase 3).

### 5.1 상태 바 알림의 결

하단 상태 바 하나로 모든 알림을 내보내므로, 두 축으로 구분한다.

| | 색 | 수명 |
|---|---|---|
| **정보** — "순환2 칸 없음 → 순환1", "상시 칸에 넣었다: src" | 보조색 | 몇 초 뒤 사라짐 |
| **거절** — "그 자리에는 다른 타일이 있다", "이미 상시 칸에 있다" | 빨강 | 몇 초 뒤 사라짐 |
| **실패·경고** — 저장 실패, 열지 못함, 배치에서 타일을 뺌, 부분 실패 요약, "같은 작업 관리가 두 창에 떠 있을 수 있다", "이 창은 신호를 받지 못한다" | 빨강 | **남는다** |

거절이 스스로 사라지는 이유: 화면이 이미 "안 움직였다"고 답하고 있으므로 문구는 이유를
한 번 알려 주면 된다. 반대로 실패·부분 실패 요약이 사라지면 무엇이 안 됐는지 알 길이
없어지므로 사용자가 다음 동작을 할 때까지 남는다. 사라지는 타이밍은 뷰가 재고,
뷰모델은 "사라져도 되는 메시지인가"만 안다.

**메시지를 세우는 순서가 계약이다.** 뷰모델은 플래그를 먼저 세우고 문구를 **마지막에** 쓴다.
문구 대입이 알림을 내고, 뷰는 그 알림을 받은 **그 자리에서** "사라져도 되는가"를 읽기
때문이다 — 문구를 먼저 쓰면 뷰가 **직전 메시지의 플래그**를 읽어 수명 타이머가 서지 않는다.
실제로 그 결함이 있었고(D30) 앱을 켠 뒤 첫 거절이 영영 사라지지 않았다. 메시지를 세우는
자리는 **하나로 모은다** — 순서를 여러 자리에 흩으면 같은 결함이 돌아온다.

**등급을 가리지 않고 메시지를 지우는 자리를 두지 않는다.** 창 활성화 재조회(§8)가 무조건
지우고 있었고, 그래서 **남아야 할 실패가 다른 프로그램에 갔다 오는 것만으로 사라졌다**(D31).
지우는 쪽도 "사라져도 되는 메시지인가"를 보고 지운다. 그 대가로 **`F5` 로도 낡은 실패가
지워지지 않는다**(→ §11).

**거절과 실패는 뷰모델 안에서도 다른 통로로 흐른다.** 패널은 자기 화면에 알림을 올리지 못해
바깥에서 받은 통로로 넘기는데, 그 통로가 하나면 거절과 실패가 같은 등급이 된다. 그래서
**둘을 따로 받는다**(D28). 거절 통로 없이 만들어진 패널은 **실패 통로로 떨어진다** — 새로
만드는 자리가 통로를 잊어도 알림이 조용히 사라지지는 않는다.

## 6. 창 위치 & 인스턴스 관리 (Phase 4)

### 6.1 창 위치 복원

- 워크스페이스별로 마지막 창 위치를 저장한다: x, y, width, height, 최대화 여부.
  **`monitorId` 는 쓰지 않는다**(§7.1 — Phase 4 Stage 0 결론). 모니터를 식별하는 문자열이
  케이블·도킹 후에도 같은 모니터를 가리키는지 확인할 수 없었고, 판정을 좌표 하나로 두면
  모니터를 뽑든 배율을 바꾸든 규칙이 하나다.
- 저장 단위는 **WPF DIP**(창의 Left/Top/Width/Height 그대로). 저장 시점은 §5 의 기존 규칙대로
  **변경 즉시 저장(디바운스)** — 창 이동·리사이즈는 이벤트가 쏟아진다.
- **변환은 비교 시점에 한 번만 한다.** 모니터 작업영역은 시스템 DPI 공간의 좌표로 오므로
  DIP 로 환산해 저장값과 비교한다. **두 군데서 변환하면 조용히 어긋난다.**
- 최대화 상태여도 좌표는 **복원 크기**를 저장한다. 최대화 상태의 Left/Top 을 저장하면
  최대화를 풀었을 때 갈 자리가 없어진다. 복원 순서는 **좌표 방어 → 창 표시 → 최대화**다.
  최대화를 창 표시 앞에 걸면 주 모니터로 끌려온다(실측).
- **런처 창의 위치는 저장하지 않는다.** 저장할 자리가 `settings.json` 인데 그 파일은 이미
  프로세스 경합을 한계로 안고 있다(§6.2).

**화면 밖 방어(필수)**: 저장 위치가 지금 화면에서 되찾을 수 있는 자리인지 검사한다. 이 검사가
없으면 창이 안 보이는 곳에 떠 못 찾는 사고가 난다.

- "어느 모니터에도 안 걸림"만 보는 것으로는 부족하다 — **1픽셀만 걸쳐도 통과**하는데 그런 창은
  사실상 못 찾는다. 그래서 **겹침이 되찾을 만한 크기인지**를 본다: 작업영역과의 겹침이
  **가로 160 DIP · 세로 32 DIP 이상**이고 **제목줄이 작업영역 안**에 있어야 통과다.
  근거(실측): 캡션 버튼 3개가 108 DIP, 제목줄 23 DIP + 테두리 4 DIP.
- **좌표의 부호로 판정하지 않는다.** 음수 좌표가 정상인 구성이 흔하다(주 모니터 왼쪽에 놓인
  모니터의 작업영역은 예컨대 `-1440, -271` 에서 시작한다).
- 저장된 크기가 현재 작업영역보다 크면 **작업영역에 맞춰 줄인다**(큰 모니터에서 작은 모니터로
  바뀐 경우).
- 통과하지 못하면 **주 모니터 중앙 + 기본 크기.** 기본 크기도 작업영역보다 크면 줄인다.
- 방어가 발동했거나 크기를 줄였으면 **§5.1 "정보"(사라지는) 등급**으로 알린다 — 실패가 아니므로
  남기지 않되, "내가 둔 자리가 아닌데" 하는 순간은 없앤다.
- **창 최소 크기는 메인 `640 x 480` DIP · 런처 `520 x 420` DIP** 다. 메인 폭의 하한을 정하는
  것은 컬럼 제약이다 — 왼쪽 `MinWidth 220` + 스플리터 `6` + 오른쪽 `MinWidth 380` = 606 에
  창 테두리 8 을 더해 614 이고, 툴바는 그보다 먼저 깨지지 않는다. 높이는 툴바·상태 바·창 크롬
  91 을 뺀 나머지를 4행 그리드가 나눠 **한 칸에 breadcrumb 과 파일 몇 줄이 함께 보이는 선**이다.
  런처는 카드 하나가 온전히 보이는 크기다.
- **값은 한 곳에만 둔다.** 메인 창의 최소 크기는 `WindowPlacement` 의 상수이고 창 XAML 이
  그것을 가리킨다 — 두 군데서 클램프하면 조용히 어긋난다(§6.1 좌표 변환의 "두 군데서 변환하면
  조용히 어긋난다"와 같은 결). 런처는 창 위치를 저장하지 않아 클램프 경로가 없고 값이 XAML
  에만 있다. 나중에 런처 위치를 저장하기로 하면 이 값도 `WindowPlacement` 로 옮긴다.
- **작업영역이 그 최소 크기보다 작으면 창이 화면을 넘는 쪽을 고른다.** 최소 크기 아래로 줄이면
  레이아웃이 깨져 못 쓰는 창이 되지만, 넘치는 창은 제목줄만 잡히면 옮길 수 있다. 이때도 위의
  겹침 하한(160 x 32)과 "제목줄이 작업영역 안"은 그대로 본다. 이 경로로 들어왔으면 §5.1
  **정보**(사라지는) 등급으로 알리며, 문구가 축소 알림과 다르다 — 최소 크기로 띄웠고 화면을
  넘을 수 있다고 말한다. **이렇게 구현했지만 실측한 것은 아니다** — 작업영역을 `640 x 480`
  보다 작게 만들 수 없어 이 경로에 도달하지 못했다(→ §11).

### 6.2 인스턴스 관리

- **워크스페이스당 프로세스 하나.** 이미 열린 워크스페이스를 다시 열려 하면 **아무 일도 하지
  않는다**(Phase 6 개정 — 이전에는 그 창을 앞으로 가져왔다). 선택 창은 그 자리에 남아 있으므로
  다른 것을 고르면 된다. 왜 안 열렸는지는 카드의 `열려 있음` 이 말한다(§3.1).
- **서로 다른 워크스페이스는 동시 다중.** 워크스페이스마다 프로세스가 따로여서 작업줄·
  `Alt+Tab` 에 따로 잡히고, 하나가 죽어도 나머지가 산다. 각 창이 자기 창 위치를 독립적으로
  기억한다.
- 이유: 같은 워크스페이스 두 번 열면 두 창이 종료 시 창 위치를 서로 덮어쓰는 충돌이
  생긴다. 워크스페이스당 하나로 두면 원천 차단되고, "동시 다중"은 서로 다른 워크스페이스로 충족.
- ~~**런처도 하나로.**~~ — **Phase 6 에서 폐기.** 선택 창을 단일화하면 그 창이 떠 있는 동안
  exe 재실행이 막혀 **두 번째 워크스페이스를 열 수 없다.** 대가로 선택 창이 둘 이상 뜰 수 있으나,
  배지는 런타임 판정(§3.1)이라 어느 창에서 봐도 답이 같다 — 「두 벌이면 배지가 서로 달라진다」는
  원래 근거는 성립하지 않았다.

#### 명령줄
- `--workspace {guid}` — 런처 없이 그 워크스페이스로 직행.
- `--launcher` — `skipLauncher`(§7.2)를 무시하고 런처를 강제로 띄운다. 자동 열기가 켜져 있으면
  인자 없는 실행이 워크스페이스로 가버려 **다른 워크스페이스를 열 자리가 없어지기** 때문이다.
- 둘이 같이 오면 **워크스페이스가 이긴다.** `--launcher` 는 "자동 열기를 무시하라"는 약한
  요청이고, 워크스페이스 지정은 무엇을 열지 못박는 강한 요청이다.
- **읽지 못한 인자로 실행을 막지 않는다.** 런처는 뜨고, 왜 그렇게 됐는지 말한다(모달 아님).

#### 탐지와 신호
- 탐지 = **세션 범위 뮤텍스**(워크스페이스 GUID 기반). **파이프는 「열려 있다」는 표식이다**
  (Phase 6 개정 — 이전에는 "앞으로 가져오기" 신호 통로였다). 서버는 그대로 만들되 아무도 그리로
  신호를 보내지 않으며, §3.1 배지가 이름공간 열거로 이것을 본다(§11).
- **둘의 유효 범위를 세션으로 맞춘다** — 뮤텍스는 `Local\` 접두사로, 파이프는 이름에 세션 id
  를 넣어서(`FolderDeck.s{SessionId}.{guid}`). 파이프 이름공간은 머신 전역이라 접두사 같은
  수단이 없으므로 이름에 넣는다. 맞추지 않으면 다른 세션에 같은 워크스페이스가 떠 있을 때
  뮤텍스는 얻는데 파이프 서버는 못 만드는 창 — 즉 **"신호를 받지 못하는 창"** 이 된다.
- 인스턴스 상태는 **JSON 에 저장하지 않는다.** OS 자원이다.
- **소유자가 죽어 버려진 뮤텍스는 인수한다.** 남은 이름 때문에 워크스페이스를 영구히 못 여는
  상태를 만들지 않는다.
- **좀비 처리**: 뮤텍스는 잡혀 있는데 **파이프 이름이 없으면** 막지 않고 연다(Phase 6 개정 —
  판정 수단이 신호 왕복에서 이름공간 열거로 바뀌었을 뿐 규칙은 그대로다). 그리고 §5.1 의
  "실패·경고"(남는 등급)로 같은 작업 관리가 두 창에 떠 있을 수 있다고 알린다. 못 열게 막으면
  사용자에게 빠져나갈 길이 없고, 감수하는 해악은 위의 창 위치 덮어쓰기 하나로 한정된다.
- 파이프 서버를 만들지 못한 창도 조용히 넘기지 않는다 — "이 창은 열려 있음으로 보이지 않는다"를
  남는 경고로 띄운다. 배지가 그 창을 놓치고 같은 워크스페이스가 좀비로 판정돼 두 번 열릴 수 있다.

#### 알려진 한계 (감수한다)
- **다른 사용자 세션**(원격 데스크톱·빠른 사용자 전환)에는 같은 워크스페이스가 또 열린다.
  이름을 세션 범위로 둔 결과다. 세션을 넘어 창을 앞으로 가져올 수는 없으므로 단일화해도
  거절밖에 할 수 없고, 이름을 머신 전역으로 되돌리면 위의 "신호를 받지 못하는 창"이 돌아온다.
  그때 §6.1 의 창 위치가 서로 덮어써지는 것을 감수한다. **두 세션으로 실측한 것은 아니다**(→ §11).
- **띄운 직후 잠깐은 파이프 이름이 없다.** 그 구간에 같은 워크스페이스를 열려 하면 좀비로
  판정돼 창이 하나 더 뜬다(경고가 남으므로 사용자에게 보인다). 파이프 서버는 창을 띄운 뒤에
  시작한다(리스너가 창 참조를 필요로 한다). 이 구간이 실제로 얼마나 되는지는 실측하지 않았다
  (→ §11).
- **`settings.json` 을 두 프로세스가 쓸 수 있다.** 원자적 교체라 파일이 깨지지는 않지만 나중에
  쓴 쪽이 이긴다(잃는 것은 `lastWorkspaceId` 한 값). **`lastWorkspaceId` 는 워크스페이스를 연
  그 프로세스가 적는다**(Phase 6 개정 — 선택 창이 그 프로세스 자신이므로 「런처가 적는」 분기가
  없어졌다).

**저장하지 않는 런타임 값**: 타일 `currentPath`, 파일 선택 상태, 폴더 접근 가능 여부,
배치 편집 모드 on/off, **검색 타일의 질의 문자열과 결과**(§4.12).

**스키마 버전 이력** — 지금까지 전부 *필드 추가*뿐이라 구버전 파일을 거부하지 않는다.
없는 슬롯은 기본값으로 읽고, 저장할 때 최신 버전으로 승격한다. `> CurrentSchemaVersion`만
하드 실패다.
- v1 — 최초.
- v2 — `leftLayout` 추가.
- v3 — `grid`·`tiles` 를 실제로 사용 + `tiles[].rotationIndex`, `folders[].rotationSlot` 추가.
  `tiles` 가 비어 있으면 상시 폴더마다 타일 하나 + 순환1 타일 하나를 균등 배치로 유도한다.
- v4 — `onConflict`·`askOnConflict` 추가(§4.3). 둘 다 없으면 "겹치면 물어보고, 안 정했으면
  덮어쓴다"는 기본값이라 v1~v3 파일의 동작이 그대로다.
- v5 — `window` 를 실제로 사용 + `window.maximized` 추가(§6.1). `window` 자체는 v1 부터 있던
  예약 슬롯이라 채우는 것만으로는 버전이 오르지 않았고, `maximized` 한 필드가 늘어 5 가 됐다.
  없으면 `false`(최대화 아님). **`monitorId` 는 v5 에서 쓰지 않는다** — 채우지 않고 읽지도
  않는다. 다만 구파일에 값이 있으면 **지우지 않고 그대로 왕복한다**(무손실 왕복). 판정에
  관여하지 않는 잔여 값이며, 이 왕복은 `WorkspaceRoundTripTests` 가 지키는 성질이다.
- v6 — `leftLayout.leftPanelCollapsed`·`folders[].foldersFirst` 추가(Phase 8-E). 둘 다 순수
  추가고, 없으면 기본값(펼침 · 폴더 먼저)으로 읽히는데 **그 기본값이 Phase 8-E 전의 실제
  동작**이라 마이그레이션 코드가 없다. `foldersFirst` 를 `bool` + 초기화자 `= true` 로 둔 것이
  핵심이다 — 초기화자가 없으면 슬롯 없는 구파일이 `false`(통합 정렬)로 읽혀 **목록 순서가
  조용히 바뀐다.** v4 의 `askOnConflict` 가 `bool?` 인 것과 같은 종류의 함정이다.
- v7 — `tiles[].kind` 에 `search` 가 는다(Phase 12 · D69 · §4.12). **값이 느는 것이지 필드가
  느는 것이 아니다** — 구파일에는 `search` 가 없으므로 읽기가 그대로고 마이그레이션 코드도
  없다. 검색 타일은 **`folderId` 를 갖지 않는다**(`kind` 가 `pinned` 일 때만 있다).
  - **워크스페이스당 하나만 둔다.** 둘 이상이 든 파일을 만나면 **첫 하나만 살리고 나머지는
    빈 칸으로 읽는다.** 거부하지 않는 이유는 §4.11-1 과 같다 — 사람이 손으로 고칠 수 있는
    파일이고, 워크스페이스 자체를 못 열게 되는 쪽이 더 나쁘다.
  - ~~모르는 `kind` 값을 만나면 빈 칸으로 읽는다.~~ — **틀렸다. D69-c 에서 실물을 보고
    고쳤다.** 이 저장소는 **모르는 열거자 값을 조용히 넘기지 않는다** — `FolderDeckJson`
    이 `JsonStringEnumConverter(camelCase, allowIntegerValues: false)` 를 걸어 두었고,
    모르는 값은 `JsonException` 이 되어 **워크스페이스 파일 전체가 `CorruptData` 로**
    보고된다. 빈 칸이 되는 것이 아니라 **그 파일이 안 열린다.**
    - **그 동작을 그대로 둔다.** 커스텀 컨버터로 조용히 넘기는 쪽은 「모르는 값을 기본값으로
      뭉개지 않는다」는 저장 계층의 결정을 뒤집는 일이고, 그 결정은 손으로 고친 파일을
      조용히 망가뜨리지 않으려고 세운 것이다(§5).
    - **곁가지 하나** — 구버전 앱이 v7 파일을 열면 「이 버전이 모르는 형식이다」가 아니라
      **「JSON 을 읽을 수 없다」**가 뜬다. `schemaVersion` 검사가 역직렬화 **뒤**에 있어서
      `kind` 가 먼저 터지기 때문이다. 하드 실패라는 결론은 같고 문구만 어긋난다.
      **고치지 않는다** — 읽기 순서를 뒤집는 변경이고, 구버전 앱으로 되돌아가는 것은
      이 도구에서 주변적인 경우다.
- v8 — `folders[].showSize`·`folders[].showModified` 추가(Phase 15 · D79 · §3.2). 둘 다 순수
  추가고, 없으면 `true`(둘 다 보인다)로 읽히는데 **그 기본값이 Phase 15 전의 실제 동작**이라
  마이그레이션 코드가 없다. **`bool` + 초기화자 `= true` 로 둔 것이 핵심이다** — 초기화자가
  없으면 슬롯 없는 구파일이 `false` 로 읽혀 **열 둘이 조용히 사라진다.** v6 의 `foldersFirst`
  와 같은 종류의 함정이다.
  - **열 이름을 값으로 싣는 배열이 아니라 필드 둘이다.** 배열로 두면 열거자는 모르는 값에서
    파일 전체가 `CorruptData` 가 되고(v7), 문자열은 오타를 조용히 넘긴다. 토글 대상이 정확히
    둘이므로 필드 둘이 더 싸다. **열이 늘면 필드가 는다** — 그 비용은 감수한다.
  - **`위치` 열은 여기 없다.** `위치` 는 **검색 중일 때만 존재하는 열**이라 폴더의 항구적
    성질이 아니다 — 폴더에 저장하면 검색을 안 할 때도 그 값이 남는다. 재귀 검색 중인 폴더
    타일에는 `Entry` 가 있지만 **거기에도 안 넣는다**(D80-b).
  - **검색 타일은 이 칸을 아예 쓰지 않는다.** `folderId` 를 갖지 않아 `folders[]` 항목을
    가리킬 수 없다(v7). 검색 뷰의 열 표시는 **저장하지 않는다**(§3.2) — 질의 문자열·결과·
    정렬과 같은 층이다. 나중에 검색 타일의 상태를 영속으로 만들 때 정렬과 **함께** 한 회차로
    옮긴다.

### 7.2 전역 설정 — `%APPDATA%\FolderDeck\settings.json`
```
{
  "schemaVersion":   4,
  "skipLauncher":    false,        // "마지막 작업 자동 열기"
  "lastWorkspaceId": "GUID",
  "workspaceOrder":  [ "GUID", "..." ],  // 런처 표시 순서(옵션)
  "tileGap":         8,                  // v2. 타일 사이 여백(§3.2). 4/6/8/12/16 · 없으면 8.
  "extensionGlyphs": { ".pdf": "📕" },  // v3. 확장자별 글리프(§3.3). 없으면 빈 사전.
  "showShellIcons":  true,               // v4. 아이콘 3단의 ② 단(§3.2). 없으면 true.
  "everythingMaxResults": 1000           // v4. 전역 검색 결과 상한(§4.12). 없으면 1000.
}
```
**스키마 버전 이력** — 워크스페이스(§7.1)와 **따로 오른다.**
- v1 — 최초.
- v2 — `tileGap` 추가(D56 · §3.2). 없으면 **8**(그전의 실제 간격)로 읽고, 램프 밖 값이 들어
  있어도 8 로 떨어뜨린다. **두 경우를 서로 다른 장치가 막는다** — 슬롯 없음은 뒷필드
  초기화자가, 램프 밖 값은 속성 setter 가 막는다. 이 파일은 사람이 열어 손으로 고칠 수 있어
  아무 숫자나 들어올 수 있고, 기본값이 8 이 아니면 **옛 설정의 화면이 조용히 바뀐다** —
  §7.1 v6 의 `foldersFirst` 와 같은 종류의 함정이다.
- v3 — `extensionGlyphs` 추가(D59 · §3.3). 확장자 → 글자 한 자의 사전이다. **이 저장소가
  사전을 JSON 에 담은 첫 자리다** — 그전에는 리스트(`workspaceOrder`)뿐이었다.
  - **없으면 빈 채로 읽는다.** 슬롯이 없어도, `null` 이 명시돼 있어도 빈 사전이다 —
    v2 의 `tileGap` 과 같이 **두 경우를 서로 다른 장치가 막는다.**
  - **키는 소문자 + 앞점으로 정규화한다.** `PDF` · `.PDF` · `.pdf` 가 모두 `.pdf` 한 키로
    떨어진다. 정규화는 **한 함수만** 지난다 — 넣을 때와 찾을 때가 다른 규칙을 쓰면 조용히
    안 맞는다.
  - 확장자 칸이나 글자 칸이 **빈 행은 저장하지 않는다.** 점 하나(`"."`)는 유효한 키다 —
    이름이 점으로 끝나는 파일에 실제로 그 값이 나온다. 두 행이 같은 키로 정규화되면
    **나중 행이 이긴다.**
- v4 — `showShellIcons`·`everythingMaxResults` 추가(Phase 12 · D69 · §3.2·§4.12).
  - `showShellIcons` — **없으면 `true`.** `bool` + 초기화자 `= true` 로 둔다. 초기화자가
    없으면 슬롯 없는 구파일이 `false` 로 읽혀 **셸 아이콘이 조용히 사라진다** — §7.1 v6 의
    `foldersFirst` 와 같은 함정이다.
  - `everythingMaxResults` — 없으면 **1000**. 고르개 밖의 값(`200/500/1000/2000/5000`)이
    들어 있으면 **속성 setter 가 1000 으로 떨어뜨린다** — v2 의 `tileGap` 과 같은 장치이고,
    슬롯 없음은 뒷필드 초기화자가 따로 막는다.

다크 테마를 착수하면 `theme` 필드가 는다(`doc/FolderDeck_familylook_spec.md` §7).
**지금 필드를 만들지 않는다** — 쓰지 않는 슬롯을 미리 두면 읽는 쪽이 기본값 처리를 먼저
하게 된다. 워크스페이스 스키마(§7.1 · 현재 **6**)와는 무관하다.

직렬화는 **System.Text.Json**(내장). Newtonsoft는 특별한 이유 없으면 쓰지 않는다.

## 8. 기술 스택 & 구현 메모

- **.NET 10 (`net10.0-windows`) · WPF.** 트리/리스트+상세 뷰, 데이터 바인딩에 적합.
- **MVVM = CommunityToolkit.Mvvm**(`ObservableObject`, `[RelayCommand]`). App 쪽에만 참조.
- 폴더 리스트: `ItemsControl`. 파일 목록: `ListView`의 `View`를 폴더 뷰 방식대로 전환
  (`GridView` 상세 / `SimpleList` 목록 — **아이콘 격자가 아니라 세로 한 줄 리스트**다.
  목록 쪽에는 **컬럼 머리가 아예 없다** — 그래서 `list` 뷰에서는 머리글 클릭이 정렬 진입점이
  될 수 없다. 상세 뷰에서는 Phase 8-B 부터 머리글 클릭이 정렬한다, §3.2).
- 폴더 열거는 **async**, 목록은 **가상화 켬**(로그 수천 개 폴더에서 UI 멈춤 방지).
- 갱신을 일으키는 자리는 **넷이다** — 수동(F5) · 창 활성화 시 재조회 · **조작 후** · **폴더
  감시**. 마지막 하나가 `FileSystemWatcher` 다. 감시자는 seam 에 얹힌 것이 아니라 **네 번째
  자리로 직접 들어갔다.**
  > **「갱신 자리들이 서로 다른 층에 직접 박혀 있어 공통 진입점이 없다」는 원래 서술을
  > 2026-08-21 코드 조사가 뒤집었다.** 위쪽 층이 갈려 있는 것은 맞다 — `F5` 와 창 활성화는
  > `RefreshAllCommand` 하나로 합류하고 조작 후만 `RefreshAllPanelsAsync` 로 따로 간다.
  > 그러나 **넷 다 마지막에는 `FolderPanelViewModel.RefreshAsync()` 를 지난다.**
- **감시자가 죽으면 재조회가 되살린다**(D37). 패널이 목록 읽기를 끝낼 때마다 신호를 하나 내고,
  감시자가 그것을 듣다가 **자기가 죽어 있으면** — `_watcher` 가 `null` 인데 볼 경로는 있는 상태
  — 배경 스레드에서 새 인스턴스를 만든다. 되돌아와 필드에 넣는 것은 UI 스레드다.
  **주기 점검·하트비트·시간 기반 유예는 두지 않는다** — 「이미 시도 중이면 새로 시작하지
  않는다」 하나로 반복 비용이 막힌다. `F5` 만 예외로 가르는 배선도 없다. 신호는 성공·실패를
  가리지 않고 내므로 **「접근 불가」 배너의 「다시 시도」도 같은 경로를 지난다.**
  **패널은 감시자를 모르는 채로 남는다** — 의존은 지금처럼 한 방향이다.
  > **실환경 검증은 못 했다**(→ §11). 감시자가 죽는 상황을 재현하지 못했다.
- 파일 복사/이동: 앱 내부 상태로 처리. 다중 목적지는 반복. 폴더는 재귀.
- **DPI 인식은 `app.manifest` 에 System 으로 명시한다.** 명시하지 않으면 WPF 가 첫 창에서
  스스로 올리므로(실측: `Main` 진입 시 무인식 → 창 생성 후 System), **창을 만들기 전에 도는
  코드가 다른 좌표계에서 좌표를 판정한다.** §6.1 의 저장 위치 판정이 성격상 그 자리다.
  값이 지금의 사실상 동작과 같아 렌더링은 달라지지 않는다(실측으로 확인).
  **PerMonitorV2 로 가지 않는다** — 가면 DIP↔픽셀 계수가 모니터마다 갈려 §6.1 의 변환이
  복잡해진다. 배율이 다른 모니터에서의 렌더링 선명도는 창 위치와 별개 주제다.
- 휴지통 삭제 / 모니터 작업영역 / 인스턴스 단일화 / 셸 컨텍스트 메뉴는 Win32·셸 interop
  영역 — 정확한 API/시그니처는 코드에서 확인(→ §11). 전부 Phase 1 밖.
- **테마 교체는 재시작 범위다.** 시작 시 설정값으로 색 딕셔너리를 골라 병합하고, 런타임
  교체는 지원하지 않는다. 색 참조가 전부 `StaticResource`(239곳)이므로 실행 중에 딕셔너리를
  갈아끼워도 반영되지 않는다 — 239곳을 `DynamicResource` 로 바꾸지 않는다. 얻는 것이
  "재시작 없이 바뀐다" 하나인데, 워크스페이스를 여는 것 자체가 창을 새로 띄우는 동작이다
  (§6.2 — 워크스페이스당 프로세스 하나). 근거는 `doc/FolderDeck_familylook_spec.md` §7.
- **컬럼 폭을 계산할 때 뷰포트 폭은 `ScrollViewer.ViewportWidth` 에서 가져온다**(부채 23) —
  `ActualWidth` 는 세로 스크롤바를 포함하므로(실측 17px 차) 그 값으로 계산하면 컬럼이 넘쳐
  가로 스크롤이 생긴다. 컬럼 폭을 만지는 코드가 또 생기면 같은 자리를 밟는다.
- **`ListViewItem` 의 `Template` 을 다시 쓰면 컬럼이 사라진다** — `GridViewRowPresenter` 가
  함께 죽기 때문이다(실측). 항목 모양을 바꿀 일이 생기면 `Template` 교체가 아니라 색 토큰과
  트리거로 처리한다.
- **항목 Style 의 트리거가 테마 트리거를 이긴다**(실측). 선택 강조 색을 테마 딕셔너리 쪽에서
  덮으려 해도 항목 Style 쪽이 먼저 적용된다.
- **`Brush.SelectionSurface` 는 선언값과 실제 렌더가 다르다** — 선언 `#FFCCEFFE` · 화면 실측
  `#D9F3FE`(묶음 2 실측). 토큰 값의 주인은 색 사양 문서이고, 이 차이는 여기에만 적는다.
- **테스트 어셈블리가 MTA 라서 못 하는 것은 WPF 컨트롤 인스턴스화뿐이다**(부채 9·24 · 범위
  정정). `DependencyProperty.RegisterAttached` 는 MTA 에서도 된다 — 첨부 속성 자체를 검증하는
  테스트는 짤 수 있다. 뷰를 단위 테스트로 덮으려면 스레드 모델부터 바꿔야 한다.
- **`MetaText` 를 뷰가 더는 읽지 않는다**(테스트만 읽는다 · 부채 19). `MetaCountText` ·
  `ViewModeText` · `MetaSortText` 세 조각의 합으로 정의해 두어 드리프트는 막았다.
- **`sortBy` 의 `type` 은 확장자다**(`Path.GetExtension` · 대소문자 무시). 헤더 메타의 UI 라벨은
  **"종류"** 로 둔다 — 문구와 동작이 어긋나지만 "확장자"보다 읽기 쉬워 v1 은 라벨을 지켰다.
- **`ClearSelection` 은 목록을 뒤집은 뒤에 불러야 한다**(부채 20). 이 순서 의존성을 지키는
  테스트가 없다 — 위의 MTA 제약 때문이다. 코드 주석 한 줄이 최소 방어다.
- **같은 `FolderEntry` 가 두 패널에 동시에 뜨면 한쪽의 전환이 다른 쪽에 즉시 보이지 않는다**
  (부채 18). 코웍은 "코드로는 그 상태가 만들어지지 않는다"고 했고 **손 재현은 하지 않았다** —
  **추론이며 관측이 아니다.**
- ~~**알려진 플레이크 둘**(부채 8)~~ — `ConflictPolicyTests.RememberingStopsTheAskingAndPersists` ·
  `AnchorNavigationTests.CurrentPathIsNeverPersisted`. **기전은 닫혔다.**
  `DebouncedSaveScheduler.Flush()` 가 **진행 중인 쓰기를 기다리지 않아** 사전이 빈 것만 보고
  돌아왔고, 그래서 "밀린 쓰기를 지금 모두 수행한다(동기)"가 깨져 있었다. 쓰기가 사라진 것이
  아니라 **호출자가 원자적 교체 전 파일을 읽었다.** 지금은 진행 중인 쓰기를 세어 0 이 될
  때까지 기다린다(D27). 수정 뒤 전체 스위트 **21회에 실패 0**(D27 직후 12회 · 다음 묶음 9회).
  **다만 기준선 회차에서도 나오지 않은 적이 있어 "없어졌다"의 증명은 아니다** —
  **한 번의 전체 통과를 근거로 쓰지 마라**는 규칙은 그대로다.
- **감시 갱신 1회의 비용은 디바운스에 묻힌다.** 1,000개 폴더에서 목록을 다시 읽는 왕복이
  **로컬 1ms 미만 · 진짜 NAS 최대 67ms** 다(2026-08-12 실측). 디바운스 최대 대기
  **1,000ms** 의 1/15 에도 못 미친다. 다만 **GUI 렌더를 뺀 값이다** — 목록을 실제로 그리는
  비용은 따로 재지 않았다.
- **앱 자신의 조작 중에는 감시 갱신을 삼킨다.** 조작이 끝나면 기존 갱신(조작 후 자리)이
  **전량 재조회로 갚는다.** 삼키지 않으면 1,000개를 지우는 55초 동안 목록을 **50번** 다시
  그려 창이 멈춘다(2026-08-12 실측). **같은 판정을 창 활성화 재조회가 이미 쓰고 있었다** —
  감시는 그 규칙의 **네 번째 적용**이다.
- **셸 확장이 우리 프로세스의 FPU 예외 마스크를 풀고 복원하지 않는다.** 항목 우클릭이 확장 DLL 을
  in-proc 로 올리고, `IContextMenu.QueryContextMenu` 에서 돌아오면 `MxCsr` 의 Invalid·ZeroDivide·
  Overflow 가 마스크 해제된 채 남는다(실측 `0x1F80`→`0x1920` · x87 `CW` `0x027F`→`0x1372` ·
  2026-08-19). 그 뒤 레이아웃의 **정상적인** `divsd` 가 0 으로 나누면 평소의 `±Infinity` 대신
  하드웨어 예외 `0xC000008E` 가 되고, .NET 10 의 `RhThrowHwEx` 매핑표에 부동소수점 코드가
  **없어** `Environment.FailFast("InternalError")` 로 프로세스가 즉사한다. `FailFast` 라
  `DispatcherUnhandledException`·`AppDomain.UnhandledException`·`WM_CLOSE` 가 **하나도** 발화하지
  않는다 — 그것이 「창만 조용히 사라진다」의 정체였다.
- **대응은 `FpuGuard` 스코프다.** 제3자 코드가 도는 자리 **열넷**을 스코프 **열셋**으로 감싸
  빠져나올 때 예외 마스크를 되돌린다(`_controlfp_s` · `_MCW_EM`). 자리마다 손으로 저장·복원하지
  않는다. `DisplayItems` 교체 자리에 그물 하나를 두어 감싸지 못한 경로를 잡는다.
  **런타임 우회는 없다** — `LegacyExceptionHandling` 스위치는 `release/9.0` 에 있고 `v10.0.8` 에는
  없다. x87 제어워드까지 함께 돌아오는지는 **확인하지 않았다** — x64 에서 부동소수점은 SSE 를
  쓰므로 요점은 `MxCsr` 다.
- **`Marshal.GetLastPInvokeError()` 를 읽는 자리보다 스코프가 먼저 닫히면 안 된다** —
  `_controlfp_s` 가 last error 를 덮는다. 셸 interop 에 손댈 때마다 이 순서를 확인한다.
- **저장소의 유일한 `InternalsVisibleTo` 는 `FolderDeck.App` → `FolderDeck.App.Tests` 다.**
  `FpuGuard` 를 `Interop/` 관례대로 `internal` 로 두고 시험이 스코프를 열고 닫게 하려고 열었다.
  타입을 `public` 으로 올리는 대안보다 관례를 덜 깬다.
- **호출부가 0 이지만 의도적으로 남긴 코드가 있다**(Phase 6 · D43). `ActivationSignal.TrySend` ·
  `ActivatePayload` · `ActivationListener` 의 앞으로-가져오기 경로 · `WindowActivation` ·
  `IInstanceSignals.TrySendActivate` — 「그 창을 앞으로」 수단 일체다. 상주 런처를 없애면서
  부르는 곳이 사라졌으나 **지우지 않았다.** FolderDeck·TerminalDeck·WebDeck 을 묶는 프로젝트
  층이 워크스페이스 창을 앞으로 부를 때 쓸 수단이고, Stage 0 실측으로 얻은 조합(보내는 쪽
  `AllowSetForegroundWindow` + 받는 쪽이 올리기)이라 지웠다 다시 만들면 그 실측을 다시 해야
  한다. **다만 실물 동작은 Stage 0 이후 재확인한 적이 없다** — 남겼다는 것이 지금도 맞다는
  뜻은 아니다. 시험 여섯이 프로세스 안 파이프 왕복까지만 문다.
- **`lastWorkspaceId` 를 실제로 적는 자리는 시험이 닿지 못한다**(Phase 6 · D42-fix). 적는 곳은
  `App.ShowWorkspaceWindow` 인데 위의 MTA 제약으로 `App` 을 시험에서 세울 수 없다.
  `LauncherCardTests` 는 **뷰모델이 적지 않는다**는 음의 단언만 문다 — 「두 곳에서 적지
  않는다」는 지켜지지만 「한 곳에서는 적는다」는 손 확인뿐이다.
- **`DropWatch` 의 해제가 `try/finally` 밖에 있다**(D52 조사). 내보내기 드래그가 예외로
  나가면 창에 `PreviewDrop` 관찰자가 남고 드래그마다 쌓인다. **드롭을 막지는 않는다** —
  몸통이 「앱 안에 놓였다」를 기록하는 한 줄뿐이다(§4.9). 고치지 않았다.
- **드래그 배선을 무는 시험이 하나도 없다**(D52 조사). `AllowDrop` · XAML 이벤트 배선 ·
  히트테스트를 물려면 `MainWindow` 를 세워야 하는데 시험 어셈블리가 MTA 라 할 수 없다.
  「과녁이 켜지는가」는 **손 확인으로만** 잡힌다. 첨부 속성으로 바꿔 짜도 라우팅은 못 문다 —
  STA 하네스를 새로 세우는 것이 유일한 길이고 **그 비용은 재지 않았다.**

## 9. Phase 계획 (단계별 리뷰 게이트)

각 단계 끝에서 실제로 써보고 다음으로 진행.

- **Phase 1 — 뼈대**: 데이터 계층 → 메인 창(좌우 2단, 폴더 리스트, 실시간 표시, 클릭 시
  순환 칸 교체, 하위/상위 이동 + 앵커 복귀) → 런처. 그리드는 단순 배치.
- **Phase 2 — 그리드 배치**: 4x4, 타일 배치/리사이즈("배치 편집" 모드), 상시/순환 지정,
  다개 순환 칸 + 번호 태그, `tiles[]` 저장(schemaVersion 3).
- **Phase 3 — 파일 조작**: 단일 실행 엔진 + 대상함 + 다중 선택 복사/이동 + 드래그앤드롭 +
  매크로 + 미리보기 + 덮어쓰기 알림 + 부분 실패 보고 + 폴더 조작(재귀·진행·취소)
  + **휴지통 정리**(§4.4 — Phase 4 에서 앞당겼다).
- **Phase 4 — 창/인스턴스**: 창 위치 저장/복원 + 화면 밖 방어(§6.1),
  워크스페이스당 단일 인스턴스 + 서로 다른 워크스페이스 다중 실행(§6.2).
- **Phase 5 — 셸 연동**: 외부 드래그앤드롭 받기/내보내기(§4.9), 셸 컨텍스트 메뉴(§4.6),
  `FileSystemWatcher` 자동 갱신(§8) — **구현이 끝났다.**
  셸 연동이 여기서 처음 생기는 것은 아니다 — 런처의 폴더 드롭(§3.1)은 Phase 1+2 부터 돈다.
- **Phase 6 — 창 수명**: 상주 런처를 없앤다(§3.1·§6.2). 실행하면 선택 창이 뜨고, 고르면 그 창이
  워크스페이스 창이 된다. 이미 열린 것을 고르면 아무 일도 하지 않는다. 워크스페이스당 프로세스
  하나·서로 다른 워크스페이스 동시 다중·배지·중복 방지는 그대로 살고, 파이프는 신호 통로에서
  **「열려 있다」는 표식**으로 뜻이 바뀐다 — **구현이 끝났다**(D40~D43).
- **Phase 7 — 배포**: 자체 포함 게시 + 앱 아이콘 + 사용자별 설치 프로그램(§12) —
  **구현이 끝났다**(D45~D47). 앱 동작은 한 줄도 바뀌지 않았다. 바뀐 것은 산출물 이름·
  파일 속성·설치 수단뿐이다.
- **Phase 8 — 화면 손질**: 런처 하단 고정 바·세 줄 카드·선택 하이라이트(§3.1), 컬럼 머리
  정렬·통합 정렬·글리프 색·한 줄 타일 헤더·순환 폴더 줄(§3.2), 같은 폴더 붙여넣기(§4.3),
  스키마 v6(§7.1) — **구현이 끝났다**(8-A~8-E).
  이 페이즈는 지시서 없이 **자기완결로 돌았다** — 검증자가 게이트 값이 아니라 눈이었기 때문이다.
- **Phase 9 — 드래그 규칙 정합**: 앱 내부 드래그에 볼륨 판정과 `Shift` 를 넣고 과녁 문구가
  결과를 말하게 한다(§4.2-2) — **구현이 끝났다**(D50~D53). 탐색기와 어긋나 있던 것을 맞춘
  것이라 저장되는 값은 늘지 않았다(스키마 그대로). 배선을 무는 시험이 없어(§8) 검증자는
  게이트 값과 **JH 의 눈** 둘이었다.
- **Phase 10 — 화면 설정과 아이콘**: 타일 사이 여백을 다섯 값 중 고를 수 있게 하고(§3.2),
  **설정 창을 세워**(§3.3) 확장자별 글리프 매핑을 넣었다 — **구현이 끝났다**(D54~D60).
  `settings.json` 이 1 → 3 으로 두 번 올랐다(§7.2). 곁가지로 시험 하나의 산발 실패를 없앴다
  (D61~D62) — **원인은 못 밝혔고**, 시간에 마진을 거는 대신 결과를 기다리게 해서 없앴다.
- **Phase 11 — 셸 아이콘**: 파일 목록의 아이콘을 탐색기와 같은 모양·색으로 바꿨다(§3.2) —
  **구현이 끝났다**. 조사 둘(D66 코드 실태 · D67 비용 실측)이 앞서고, 문서를 먼저 뒤집은 뒤
  (D68-a) 취득 계층(D68-b)과 화면 배선(D68-c)으로 나눠 넣었다. **표시 계층만 바뀌고 저장되는
  값은 늘지 않았다**(스키마 그대로). 이 페이즈가 §1.2 의 「셸 아이콘은 쓰지 않는다」를
  뒤집었고, D59 확장자 커스텀이 서 있던 근거도 함께 바꿔 세웠다(§1.2).
  - 곁가지로 **드래그 씹힘 둘**을 닫았다 — 조사(D70) 뒤 판정 자리를 옮기고(D71) 끌리는 것을
    누른 항목이 정하게 했다(D72 · §4.2). **자동 시험이 못 무는 자리**라 검증자는 게이트 값과
    **JH 의 눈** 둘이었다.
  - 곁가지로 **아이콘 취득의 산발 실패**를 닫았다(D73 계측 → D74 고침). `SHGetFileInfo` 가
    스레드풀 스레드의 **첫 호출에서만** 성공을 알리며 아이콘 핸들을 안 주는 것을 실측했고
    (80회 중 7회 · 곧장 재시도하면 7/7 성공), **한 번 다시 부르고 실패는 캐시하지 않는 것**
    으로 고쳤다. **원인을 재고 고쳤다** — 시간에 마진을 걸어 덮은 Phase 10 의 D61~D62 와
    다른 자리다.
- **Phase 12 — 전역 검색**: Everything 색인을 쓰는 검색 타일을 넣었다(§4.12) — **구현이
  끝났다**. 조사 하나(D69 B-0)가 앞서고 문서를 먼저 박은 뒤(D69-a), 질의 계층(b) · 스키마와
  코드 흠(c) · 설정 창(d) · 타일 화면(e) · 정렬과 드래그(f) · 컬럼 머리(g) · 통지(h) 여덟
  회차로 나눠 넣었다. **두 스키마가 함께 올랐다** — 워크스페이스 6 → 7(타일 종류 §7.1)과
  `settings.json` 3 → 4(결과 상한 · 셸 아이콘 토글 §7.2). D68 이 미뤄 둔 셸 아이콘 토글을
  여기에 얹어 **판이 두 번 오르는 것을 막았다.** 곁가지로 남의 버그 하나를 잡았다 — 재귀 검색
  중에도 컬럼 머리가 정렬 화살표를 붙이고 있었다(Phase 8-B 부터 · §4.10).
- **Phase 13 — 「지금 보고 있는 폴더」 메뉴**: 목록의 빈 곳 우클릭에 **새 폴더 만들기**를
  넣고, 같은 메뉴에서 **지금 보고 있는 폴더를 앵커로 지정**할 수 있게 했다(§4.6 · D75) —
  **구현이 끝났다.** 조사 하나(D75 B-0 — 빈 곳 히트테스트 · breadcrumb 메뉴 · 앵커 커맨드의
  대상 · 폴더 생성 실태)가 앞서고 문서를 먼저 박은 뒤(D75-a), 계층(b) · 배선(c) · 메뉴가 뜨는
  자리 좁히기와 단축키(d) · 모달 버튼 문구(e) 네 회차로 나눠 넣었다. **저장되는 값은 늘지
  않았다**(스키마 그대로). 폴더 생성은 앱에 **처음** 들어간 기능이고 나머지 넷은 이미 있는
  커맨드에 진입점을 더한 것이다.
  - **손 확인이 결함 둘을 잡았다.** ① 검색 타일에서도 메뉴가 떠 문서 조항을 어기고 있었다.
    ② 새 폴더 모달의 확인 버튼에 「바꾸기」가 떴다 — 이름 바꾸기 모달을 그대로 재사용한
    탓이다. **둘 다 자동 시험이 못 무는 자리였다**(XAML·코드비하인드). d·e 회차가 그것을
    닫았고, ②는 문구를 `IUserPrompt` 로 흘려 **무는 자리로 바꿨다.**
  - **손 확인이 함정도 하나 드러냈다** — 목록이 가득 차면 빈 곳이 없다. `Ctrl+Shift+N`(D75-d)
    이 그 답이다.
- **Phase 14 — 프로세스 간 드롭**: 다른 FolderDeck 창(= 다른 워크스페이스 = 다른 프로세스)의
  타일로 파일을 끌면 드롭이 **통째로 거절되던 것**을 고쳤다(§4.9 · D76~D77) — **구현이
  끝났다.** 조사 하나(D76 B-0)가 앞서고 문서를 먼저 박은 뒤(D77-a) 코드 한 회차(D77-b)로
  닫았다. 원인은 사설 포맷에 **객체**를 실은 것이었다 — 객체는 프로세스 경계를 못 넘고,
  받는 쪽은 사설 포맷이 있으면 셸로 내려가지 않으므로(§4.9) 거절만 남았다. **글자(JSON)로
  바꿨다.** **저장되는 값은 늘지 않았다**(스키마 그대로).
  - **기전은 재지 않았다.** 마샬링이 어디서 어떻게 실패하는지 모르는 채로 고쳤고, 손 확인
    3/3 이 결과만 확인했다. **원인을 재고 고친 D73~D74 와 다른 자리다.**
  - **되돌림 시험이 구멍 하나를 드러냈다**(D77-b R2). 싣는 쪽을 옛 방식으로 되돌려도 자동
    시험이 하나도 안 터진다 — 실제 드래그 시작 경로를 무는 시험이 없다(§11).
- **Phase 15 — 컬럼 표시 토글**: 상세 뷰의 `크기`·`수정` 을 컬럼 머리글 우클릭으로 끄고 켤 수
  있게 한다(§3.2 · §4.6 · D78~). 조사 하나(D78 B-0 — 컬럼 머리글 우클릭 자리 · 고무줄 · 컬럼
  선언과 자동 폭 계산 · 저장 자리 · 좌클릭 정렬과의 충돌)가 앞섰다. **워크스페이스 스키마가
  7 → 8 로 오른다**(§7.1). 폭은 저장하지 않는다 — 표시 토글이라 **자동 폭 계산을 한 줄도
  안 고친다.**
  - **D78 이 하나를 닫고 하나를 갈랐다.** 컬럼 머리글 우클릭은 지금 명시로 막혀 있어 뺏을
    메뉴가 없다(§4.6). 고무줄은 코드상 시작 조건이 성립하지만 실물에서 아무 일도 일어나지
    않아 **가드를 넣지 않는다**(§4.8) — **기전은 재지 않았다.**
  - **오래된 결함 하나를 드러냈다**(D80 B-0). `NeedsLocationColumn`(재귀 검색·검색 타일에서
    `위치` 열이 붙는 판정)에 **변경 통지가 어디에도 없었다** — 값 계산은 옳은데 바뀌었다는
    소식이 안 갔다. 그래서 **재귀 검색을 켜도 `위치` 열이 그 자리에서 붙지 않았다**(§4.10 ·
    §4.12 는 붙는다고 적어 두었다). 폴더를 갈아타는 등 스타일이 다시 평가될 때에야 뒤늦게
    나왔다. **D69 부터 있던 것이고 Phase 15 의 컬럼 메뉴가 같은 판정을 읽으면서 드러났다** —
    메뉴 항목도 자기가 만들어진 순간의 값에 멈춰 있었다. **D80 이 통지를 붙여 고쳤다.**
    - **가설 둘이 실측으로 무너진 뒤에 나온 답이다.** 「`Style` 세터로 붙인 `ContextMenu` 가
      공유된다」도, 「`MultiDataTrigger` 는 조건 하나가 통지되면 나머지도 다시 읽는다」도
      **틀렸다.** 앞의 조사(D79-c)가 쓴 `XamlReader.Parse` 는 `x:Shared` 를 아예 검증할 수
      없는 도구였다 — **재는 도구가 그 속성을 볼 수 있는지부터 확인한다.**

> **Phase 3 진행 이력** — Stage 0(폴리시) → Stage 1(Core 엔진) → Stage 2(대상함 + 다중
> 복사/이동) → Stage 3(드래그앤드롭 + 휴지통 + 폴더 재귀·진행·취소) → Stage 4(동일 이름
> 충돌 선택지, §4.3) → Stage 5(매크로, §4.7). **Phase 3 완료.**
>
> **Phase 4 진행 이력** — Stage 0(환경 확인 스파이크: 모니터 작업영역·DPI·인스턴스 탐지 수단)
> → Stage 1(인스턴스 관리 §6.2, 완료) → Stage 2(창 위치 §6.1, 완료). **Phase 4 완료.**
>
> Phase 5(셸 연동)는 **구현이 끝났다**. §11 에 남은 미확인은 **넷**이다 —
> `FileSystemWatcher` 되살리기의 **검증**(구현은 D37 로 끝났다)·다른 사용자 세션 이름 충돌·
> 파이프 서버 시작 시점·최소 크기 우선 경로. 셸 컨텍스트 메뉴는 §11 에서 확인 완료로 닫혔다.
> **남은 넷은 코드가 아니라 환경이 막고 있다** — 넷 다 실환경 확인이 먼저다.
>
> **Phase 6 진행 이력** — D40(문서: 상주 런처 폐기를 §3.1·§6.2 에 반영) → D41(B-0 읽기 전용
> 조사) → D42(코드: `IWorkspaceHost` · 창 갈아끼우기 · 「이미 열려 있으면 아무 일도 안 한다」)
> → D42-fix(시험 하나를 음의 단언으로 다시 씀) → D43(상주 런처에 딸린 죽은 코드 삭제 + 툴바
> 라벨 개명). **Phase 6 완료.** 손 확인은 회차마다 셋씩 전부 통과했다.
>
> **휴지통 정리를 Phase 4 에서 Phase 3 으로 옮긴 이유**: 삭제도 `대상 집합 × 동작`이라
> Stage 1 엔진의 `Trash` 로 이미 구현돼 있었고, 남은 것이 UI 진입점뿐이었다. Phase 4 의
> 나머지(창 위치·인스턴스·셸)와는 성격이 다르다 — 그쪽은 Win32/셸 영역이고 이쪽은 파일 조작이다.

## 10. 구현 핸드오프 — Phase 1 (Claude Code 대상)

> **이 절은 Phase 1 착수 시점의 기록이며 이후 Phase 로 갱신하지 않는다.** §10.3 "빼는 것"에
> 적힌 것 중 상당수는 Phase 2~4 에서 이미 구현됐다. 현재 상태는 §9 를 본다.

실제 코드 작성은 Claude Code가 한다. 이 문서가 사양이며, Phase 1은 아래 범위·순서·검증만.

### 10.1 프로젝트 구성
- 솔루션 `<repository-root>` 아래:
  - `FolderDeck.App` — WPF (`net10.0-windows`, `UseWPF=true`), CommunityToolkit.Mvvm 참조.
  - `FolderDeck.Core` — 순수 C#(UI 의존 없음): 모델, JSON 로드/세이브, **파일 조작 엔진의
    인터페이스(§4.7, 구현은 Phase 3)**, 폴더 열거 서비스.

### 10.2 Phase 1 범위 (들어가는 것)
1. **데이터 계층**: §7 스키마 모델 + `%APPDATA%\FolderDeck\` 로드/세이브(즉시 저장 디바운스,
   임시파일→교체, 손상 시 실패 드러내기). 테스트 워크스페이스 JSON 1개.
2. **메인 창**: 좌우 2단. 왼쪽 폴더 리스트(pin/접근불가 표시) + 하단 탭 자리(내용은 비워둠).
   오른쪽에 폴더 내용 async 실시간 표시(가상화). 클릭 시 순환 칸 교체, 하위/상위 이동,
   앵커 복귀 3경로. breadcrumb + 상태 바. viewMode(list/details)·정렬 표시.
3. **런처**: `workspaces\*.json` 열거 목록 + 새로 만들기 + 열기 + "삭제=워크스페이스만" 문구.

### 10.3 Phase 1에서 빼는 것 (뒤 Phase)
그리드 배치 편집/리사이즈, 파일 조작 엔진 구현(복사/이동/휴지통), 대상함·매크로 동작,
드래그앤드롭, 창 위치 복원, 인스턴스 단일화, 셸 컨텍스트 메뉴, FileSystemWatcher.
→ 이 요소들은 **자리(스키마 슬롯·UI 탭·인터페이스)만 잡아두고 동작은 만들지 않는다.**

### 10.4 검증 게이트 (각 단계 끝 "써보고 다음")
- 데이터 계층: 테스트 JSON을 넣으면 오류 없이 로드되고, 값 변경 후 재실행 시 유지된다.
  손상된 JSON은 조용히 초기화하지 않고 실패가 보인다.
- 메인 창: 폴더 리스트가 뜨고, 행 클릭 시 순환 칸이 실시간 목록으로 교체된다. 하위 폴더
  진입·상위 이동이 되고, 3경로 중 어느 것으로도 앵커로 돌아온다. 큰 폴더에서 UI가 멈추지 않는다.
  접근 불가 폴더가 목록에서 사라지지 않는다.
- 런처: 저장된 워크스페이스가 열거되고, 새로 만들어 열면 메인 창이 뜬다.

### 10.5 진행 방식 (권장)
Phase 1을 한 번에 지시하지 말고 **10.2의 1 → 2 → 3 순서로 끊어** 각 단계 결과를 보고 다음을
지시한다. 특히 메인 창(2)까지 나오면 실제로 써보고 방향을 확인한 뒤 런처로 넘어간다.

## 12. 배포 & 설치 (Phase 7)

> 이 절은 **앱 동작이 아니라 산출물**을 정한다. 코드 동작은 §1~§8 이 정한다.

### 12.1 게시 산출물

```
dotnet publish src/FolderDeck.App/FolderDeck.App.csproj -c Release -r win-x64 \
  --self-contained true -p:PublishSingleFile=false -p:DebugType=none \
  -o artifacts/publish/win-x64
```

- **자체 포함(self-contained) · `win-x64`.** 배포 대상 PC 에 .NET 10 데스크톱 런타임이 있다는
  보장이 없다. 프레임워크 의존으로 두면 설치 프로그램이 런타임 설치를 유도해야 하고 그것이
  설치 실패의 가장 흔한 자리가 된다.
- **`PublishSingleFile` 은 쓰지 않는다.** 설치 프로그램이 폴더째 놓으므로 파일 개수가 사용자
  눈에 안 보인다. 대신 첫 실행 추출 지연과 `AppContext.BaseDirectory` 의미 변화를 떠안게 된다.
- **`DebugType=none` 으로 `.pdb` 를 뺀다.** 사용자 PC 에 갈 이유가 없다.
- **RID·자체 포함 설정을 `.csproj` 에 넣지 않는다.** 넣으면 `dotnet build` · `dotnet test` 까지
  RID 별로 돌아 산출 경로가 바뀐다. 위 명령이 유일한 게시 수단이다.

실측(D83 · 2026-09-03) — **403 개 파일 · 146,663,436 바이트**. D47 때는 401 개 ·
146,514,031 바이트였다. 늘어난 둘은 D65 가 넣은 `Everything64.dll` ·
`THIRD-PARTY-NOTICES.txt` 로 본다 — **개수 차이로 미룬 추론이고 파일 목록을 대조한 것은
아니다.**

### 12.2 어셈블리 이름과 파일 속성

`FolderDeck.App.csproj` 가 정한다 —

| 속성 | 값 | 왜 |
|---|---|---|
| `AssemblyName` | `FolderDeck` | 없으면 산출물이 `FolderDeck.App.exe` 가 된다 |
| `RootNamespace` | `FolderDeck.App` | `AssemblyName` 과 다르므로 명시해 둔다 |

| `Company` · `Product` | `JH` · `Folder Deck` | exe 속성 창·작업 관리자 표시 |
| `Version` | (여기 없다) | 루트 `Directory.Build.props` 가 정한다 — 아래 |

**판 번호는 저장소 루트 `Directory.Build.props` 한 자리에 있다**(D82). `App.csproj` ·
`Core.csproj` · 시험 프로젝트가 모두 물려받으므로 `Core.dll` 도 더는 1.0.0.0 이 아니다 —
`Core.dll` 이 어느 빌드에서나 1.0.0.0 이라 옛 판이 남아 죽었던 사고(§12.3 의 `ignoreversion`
주석)의 뿌리가 여기였다. **MSBuild 가 안 읽는 자리는 `installer/FolderDeck.iss` 뿐이므로 판을
올릴 때 손댈 자리는 `Directory.Build.props` 와 `.iss` 둘이다.**

**인스턴스 이름은 어셈블리 이름과 무관하다.** `InstanceNames.cs` 가 뮤텍스
`Local\FolderDeck.{id}` · 파이프 `FolderDeck.s{세션}.{id}` 를 문자열 리터럴로 박아 둔다(§6.2).
`AssemblyName` 을 바꿔도 §6.2 의 판정은 흔들리지 않는다. **바꾼다면 손댈 자리는 그 파일이다.**

`global.json` 이 SDK 를 `10.0.204` · `rollForward: latestFeature` 로 고정한다.

### 12.3 설치 프로그램

`installer/FolderDeck.iss` — Inno Setup 7 로 컴파일한다.

```
& "C:\Program Files\Inno Setup 7\ISCC.exe" installer\FolderDeck.iss
```

- **사용자별 설치.** `DefaultDirName={localappdata}\FolderDeck\app` ·
  `PrivilegesRequired=lowest` — UAC 승격이 없다(실측 확인). 형제 앱(TerminalDeck, Squirrel)도
  사용자별로 깔린다.
- 시작 메뉴 `{group}\Folder Deck`, 산출물 `artifacts/installer/FolderDeck-Setup.exe`.
  실측(D83) **46,536,906 바이트**. ISCC 로그의 `Compressing:` 줄이 **403 개**로 게시본
  파일 개수와 같았다 — 빠진 파일이 없다.
- **`AppVersion` 은 `FolderDeck.App.csproj` 의 `<Version>` 과 같은 값이어야 한다.** 두 자리가
  따로 들고 있어 판을 올릴 때 둘 다 손으로 고친다. 어긋나도 빌드는 통과한다 — 갈라진 값은 exe
  속성 창과 「프로그램 추가/제거」 목록에서만 드러난다.
- **`.iss` 는 순수 ASCII 가 아니다.** 지금 파일은 BOM 없이 한글 주석을 담고 있다(실측
  2026-09-03 — 1,919 바이트 중 비ASCII 702 바이트 · BOM 없음). 이 자리에 있던 「순수 ASCII 로
  쓴다」는 실물과 어긋나 있었다. **한글은 주석에만 있고 지시자 줄은 ASCII 다** — 주석이 깨져도
  컴파일 결과가 갈리지 않는 자리다. D83 컴파일은 **경고 0 건**으로 통과했다(로그 전체를
  `[Ww]arning` 로 검색). 그래도 코드페이지 판정 자체는 안 쟀다(§12.5).
- **예제에 실물로 나온 지시자만 쓴다.** `Examples\Example1.iss` 기준이다. 7 의 문법은 확인된
  범위 밖이라 기억으로 지시자를 늘리지 않는다.

**1.3.0 설치 확인 (JH 손 확인 · 2026-09-03).** 1.2.0 이 깔린 PC 에 덮어 설치해 기동했고,
다른 PC 에 새로 설치해 기동했다. 그 PC 에서 전역 검색 타일이 동작해 `Everything64.dll` 이 exe
옆에 놓인 것을 확인했으며 「프로그램 추가/제거」에 `1.3.0` 으로 보였다. **대상 PC 에 .NET 10
데스크톱 런타임이 있었는지는 기록하지 않았다** — 자체 포함(§12.1)이 실제로 필요했는지는 여전히
미측정이다(§12.5).

**설치 위치는 앱 동작에 영향이 없다.** 데이터는 `%APPDATA%\FolderDeck`(§7) 이고 그 경로는
`Environment.GetFolderPath` 로 만든다. exe 옆에 쓰는 코드가 저장소에 **0 건**이다(D45 실측).

### 12.4 라이선스 판정

Inno Setup 7.1.0 컴파일러가 배너에 `Non-commercial use only` 를 찍는다. 그러나 같은 사본의
`LICENSE.TXT` 는 이렇게 적고 있다(실물 확인) —

> Permission is granted to anyone to use this software for any purpose, including commercial
> applications, and to alter and redistribute it

**판정 — 상업 사용 허가됨. 유료 구매는 벤더의 요청이며 의무가 아니다.** 배너는 구매 요청
표시로 본다. 남는 위험은 법이 아니라 사내 심사 기준이며 그것은 이 문서가 정할 것이 아니다.
버전을 내려도 그 위험은 줄지 않는다 — 요청이 버전 불문이기 때문이다.

### 12.5 하지 않은 것

- **자동 갱신이 없다.** 새 판을 깔려면 설치본을 다시 받아 실행한다.
- **코드 서명이 없다.** 처음 실행에 SmartScreen 경고가 뜰 수 있다.
- **앱이 실행 중일 때 덮어쓰기가 어떻게 되는지 확인하지 않았다.** 403 개 중 `FolderDeck.exe`
  가 잠긴 상태의 재설치는 밟아 본 적이 없다. D83 의 덮어 설치는 앱을 닫은 상태였다.
- 설치본이 마법사 화면에 `Non-commercial` 문구를 보이는지 확인하지 않았다.
- **Inno Setup 7 이 BOM 없는 비ASCII `.iss` 를 어떤 코드페이지로 읽는지 안 쟀다.** D83 컴파일이
  경고 0 건으로 통과한 것은 실측이지만, 그것이 「한글을 무시했다」와 「시스템 ANSI 로 읽었다」를
  가르지 못한다.
- **설치 폴더에 놓인 `Core.dll` 의 판 번호를 읽지 않았다.** D83 이 게시본 사본에서
  `1.3.0.0` 을 확인했고 설치본이 그 403 개를 다 담은 것도 확인했으나, 압축을 풀고 난 사본을
  직접 읽거나 체크섬을 맞춰 본 것은 아니다.
- **대상 PC 에 .NET 10 데스크톱 런타임이 있었는지 기록하지 않았다**(§12.3). 자체 포함이 실제로
  필요했는지가 그래서 아직 미측정이다.
