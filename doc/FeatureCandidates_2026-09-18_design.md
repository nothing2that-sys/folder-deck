# FolderDeck — 기능 후보 3건 설계 (2026-09-18)

작성 코웍(Claude Code) · 대상 JH · **설계만, 구현 없음.** `design.md:1877`이 이미 정한
우선순위(① 타일 간 폴더 비교/동기화 ② 워크스페이스 내 중복 파일 찾기 ③ 배치 리네임)를
그대로 따르고, `doc/Probe_2026-09-18_followup_report.md` §4(코드 사실 조사)를 근거로 삼는다.
각 절은 **목표·비목표·UX 흐름·데이터/아키텍처를 제안**하고, 결정이 필요한 지점은 근거와
함께 "미결(JH 결정)"로 남긴다 — 코드는 한 줄도 안 건드렸다.

**공통 원칙(세 기능 다 따름):**
- 자동 실행/자동 정리는 안 한다 — 후보를 보여주기만 하고, 실제 파일 조작은 이미 있는
  파이프라인(복사/이동/휴지통, §3.2)을 사용자가 직접 실행한다. 잘못 눌러 대량 삭제·이동이
  일어나는 새 위험을 안 만든다.
- 실시간 자동 갱신은 V1에 안 넣는다 — 이 앱의 기존 철학(폴더 크기 계산도 온디맨드,
  `Review_FullAudit_2026-09-17.md:264`)과 같은 결. "지금 실행" 버튼으로 스냅샷을 뜬다.
- 내용(바이트) 비교는 V1에 안 넣는다 — `FolderItem`에 해시 필드가 없고 이 저장소에 해시
  코드가 전혀 없다(전수 검색 확인, 팔로업 보고서 §4). 이름·크기·수정일만으로 판정한다.

## ① 타일 간 폴더 비교/동기화

### 목표
두 타일(열린 폴더 뷰)을 골라 "다른 점만 보기" — 어느 쪽에만 있는 파일, 이름은 같은데
크기/수정일이 다른 파일, 동일한 파일을 구분해 보여준다.

### 비목표(V1)
- **재귀 비교 안 함.** 각 타일이 지금 보여주는 최상위 목록만 비교한다 — 하위 폴더는
  "폴더인데 다르다/같다"까지만 표시하고 안으로 안 들어간다. 이 앱의 타일 자체가 "폴더
  하나의 평평한 목록" 모델이라(재귀 검색 타일은 예외), 재귀 비교는 새 "가상 병합 트리"
  UI를 요구해 범위가 커진다.
- **내용 비교 안 함** — 위 공통 원칙.
- **자동 동기화(복사/삭제로 맞추기) 안 함** — "다른 점 보기"까지만, 맞추는 건 사용자가
  기존 복사/이동으로 직접 한다.
- **실시간 갱신 안 함** — 위 공통 원칙. 두 타일의 `FolderWatcher`를 실시간으로 합류시키는
  코드가 지금 없다(팔로업 보고서 §4 "실측 ③") — 있으면 이번 범위 밖의 새 인프라다.

### UX 흐름(제안)
1. 타일 헤더에 "비교" 진입점을 둔다. 첫 타일에서 누르면 나머지 타일 헤더에 고를 수 있는
   표시가 뜬다 — **이 앱에 이미 있는 관용구를 재사용**한다: "대상함"이 여러 후보 중
   체크박스로 목적지를 고르는 것과 같은 상호작용(`MainViewModel.cs:888-889`,
   `Tray`/`TrayEntryViewModel.IsChecked`)을 타일 헤더에도 쓴다.
2. 두 번째 타일을 고르면 비교가 실행되고, 두 타일 각각의 목록 행에 상태가 표시된다 —
   「이 타일에만 있음」·「다름」·「동일」.
3. 재비교는 "다시 비교" 버튼으로만. 비교 해제는 같은 진입점을 다시 누른다.

### 핵심 설계 결정 — 비교 대상 지정을 기존 선택과 분리한다

**제안: 비교 대상 지정은 기존 파일 선택(`SelectionOwner`)과 완전히 별개의 축으로 둔다.**
이유 — `MainViewModel.cs:894-895`(§4.8)가 "선택은 타일 하나에만 존재한다"를 명시적으로
강제하는 것은, 복사/이동 파이프라인이 "지금 선택"을 유일한 소스로 읽기 때문이다
(`Selection => SelectionOwner?.SelectedItems`, `:905`) — 이 불변이 흔들리면 복사가 엉뚱한
파일을 집을 수 있다. 비교 기능이 "두 타일을 고른다"는 것도 일종의 선택처럼 보이지만,
**이걸 `SelectionOwner`에 얹으면 파일 선택과 타일 선택이 같은 상태를 다투게 돼 그
불변이 깨진다.** 그래서 비교 대상은 파일 선택과 무관한 새 상태로 둬야 한다 — 이게 이
문서에서 가장 근거가 뚜렷한 결정이라 앞세운다.

### 데이터/아키텍처(제안)
- 위 결정에 따라, `MainViewModel`에 세션 한정 상태(예:
  `(TileViewModel Left, TileViewModel Right)? ComparePair`)를 새로 두고, 워크스페이스에
  저장하지 않는다(스키마 v9 유지, 안 건드림).
- **비교 로직은 순수 함수로.** `(IReadOnlyList<FolderItem> left, IReadOnlyList<FolderItem>
  right) → ComparisonResult` — 이름으로 매칭하고 `Size`·`ModifiedUtc`로 같다/다르다를
  가른다. `FolderItem`이 이미 이 필드들을 가지고 있어(`FolderItem.cs:12`, 팔로업 보고서
  §4) 새 데이터 필드가 필요 없다. `VirtualizingWrapLayout`처럼 MTA 시험으로 바로 검증
  가능한 자리다.
- **행 배지가 새로 필요하다.** 지금 `FileItemViewModel`엔 "행 상태 배지" 관용구가 없다
  (Glyph/아이콘뿐, 조사 확인) — `CompareStatus` 같은 표시용 열거형과 그걸 그리는 새 XAML
  요소(색/아이콘)가 필요하다. 구체적 시각 디자인은 이 문서에서 안 정한다.

### 미결(JH 결정)
- 비교 대상 지정 UX가 위 제안(타일 헤더 체크)으로 괜찮은지, 다른 방식(메뉴에서 드롭다운
  으로 두 타일 고르기)을 원하는지.
- 한쪽은 폴더, 같은 이름으로 반대쪽엔 파일이 있는 것 같은 엣지 케이스 표시 방법.
- 파일명 대소문자 차이를 "다른 파일"로 볼지(윈도우 파일시스템 기본은 대소문자 구분 안
  함 — 무시하는 쪽이 자연스러워 보이나 확인 필요).

## ② 워크스페이스 내 중복 파일 찾기

### 목표
지금 열려 있는 모든 타일을 훑어 이름·크기가 같은 후보 중복 파일을 찾아 그룹으로
보여준다.

### 비목표(V1)
- **내용 기반 완전 중복 판정 안 함** — 위 공통 원칙. "이름+크기가 같으면 후보"라는
  휴리스틱만 쓴다 — 오탐 가능성이 있다는 것을 결과 화면에 명시해야 한다.
- **열린 타일 밖 스캔 안 함.** "워크스페이스 내"라는 이름 그대로 지금 열린 타일만
  대상으로 한다. `IFolderEnumerator.ListAsync`가 임의 경로를 받을 수 있다는 것은
  확인했으나(팔로업 보고서 §4), 범위를 넓히면 "어디까지 스캔할지"를 매번 골라야 해서
  UX가 커진다 — 나중 확장 여지로 남긴다.
- **자동 삭제/정리 안 함** — 위 공통 원칙.

### UX 흐름(제안)
1. 메뉴/툴바에 "중복 파일 찾기" 커맨드 — 열린 타일 전체를 한 번 스캔.
2. 결과는 그룹 목록으로 — 후보 중복끼리 묶고, 그룹 안에 경로·타일(어느 폴더)·크기·
   수정일을 나열. 항목을 골라 휴지통으로 보내거나(기존 파이프라인 재사용) 그 타일로
   포커스 이동.
3. 재스캔은 명시적 버튼으로만.

### 데이터/아키텍처(제안)
- **입력 접점은 이미 있다.** `MainViewModel.Panels`(모든 타일의 `FolderPanelViewModel`을
  평평하게 든 자리, `MainViewModel.cs:3277`)에서 각 패널의 `Items`를 모으면 된다 — 새
  순회/열거 인프라가 필요 없다.
- **그룹핑은 순수 함수로.** `(Name, Size)` 키로 묶어 그룹 크기 2 이상만 결과로 낸다.
- **"타일이 폴더가 아닌 것을 보여줄 수 있다"는 선례가 이미 있다 — 검색 타일**
  (`design.md` §4.12, 워크스페이스 스키마의 `"kind": "pinned | rotating | search"`,
  `design.md:1392`). Everything 색인을 질의해 **여러 폴더에 걸친 결과를 한 타일 목록에**
  보여주는 게 지금도 되는 일이다 — "여러 폴더 항목을 한 목록으로" 자체는 새로운 개념이
  아니다. **다만 완전한 선례는 아니다** — 검색 타일은 (a) Everything 이 프로세스당 조건·
  결과를 하나만 갖는 제약 때문에 **워크스페이스에 하나만** 둘 수 있고(§4.12), (b) 결과가
  "그룹"이 아니라 평평한 목록이다. 중복 찾기는 여럿(그룹) 표시가 필요하고 Everything 같은
  프로세스 단일성 제약은 없다 — **`kind`에 넷째 값(예: `duplicates`)을 추가해 타일로
  올리는 방향은 유효하지만, 그룹 렌더링·복수 허용 여부는 검색 타일 코드를 그대로 베낄 수
  없고 새로 설계해야 한다.**
- 이 선례 덕에 "완전히 새 화면 종류"라던 처음 추정보다는 **비용이 낮다** — 타일
  그리드·헤더·목록 가상화 인프라(§8)는 이미 있는 것을 재사용할 여지가 생겼다.

### 미결(JH 결정)
- 결과를 검색 타일처럼 **타일 하나로** 넣을지(위 선례 재사용, `kind` 확장), 아니면 별도
  창으로 띄울지 — 전자가 기존 인프라를 더 재사용하지만 "그룹 목록"이라는 새 표시 형태는
  둘 중 어느 쪽이든 새로 만들어야 한다.
- "검색 타일은 워크스페이스에 하나만"이라는 제약을 중복 찾기 타일에도 걸지(재실행하면
  기존 결과를 덮어쓰는 쪽), 아니면 여러 개 동시에 열어 둘 수 있게 할지.
- 이름이 다르고 크기만 같은 것도 후보로 보여줄지(오탐 많음), 이름까지 같은 것만
  보여줄지 — V1 기본값.

## ③ 배치 리네임

### 목표
여러 파일을 한 번에 규칙(찾기/바꾸기·번호 매기기·대소문자 변환)으로 이름을 바꾼다.

### 비목표(V1)
- **기존 F2 단일 리네임을 확장하지 않는다.** `RenameSelectionAsync`
  (`FolderPanelViewModel.cs:1646`)는 여럿 고르면 명시적으로 거절한다
  (`:1653-1655` `"이름 바꾸기는 하나만 고른 뒤에"`) — 이건 **의도된 설계**라(§4), 배치
  리네임은 그 경로를 안 건드리고 **별도의 새 커맨드/다이얼로그**로 만든다. 기존 경로에
  회귀 위험을 안 만든다.
- **정규식 등 고급 패턴은 V1에 안 넣는 쪽을 제안** — 찾기/바꾸기(부분 문자열)·번호
  매기기·대소문자 변환 세 기본형만. 이 앱의 검색 기능도 부분 일치가 기본이고 와일드카드는
  별도 상자로 가른다(`design.md` Phase 12 D69) — 같은 원칙("복잡한 문법은 별도, 기본은
  단순")을 여기도 적용하자는 제안이다.

### UX 흐름(제안)
1. 여러 파일을 고른 상태에서 컨텍스트 메뉴/단축키로 "일괄 이름 바꾸기".
2. 규칙 다이얼로그 — 입력하는 즉시 **미리보기 표**(현재 이름 → 바뀔 이름, 파일당 한 줄)를
   보여준다.
3. 이름 충돌(바뀐 이름이 이미 있음, 또는 두 파일이 같은 이름으로 수렴)이 있으면 그 줄을
   눈에 띄게 표시하고 확인 버튼을 막는다.
4. 확인 시 항목별로 `Directory.Move`/`File.Move`를 반복 호출 — 기존 저수준 동작
   (`MainViewModel.RenameFromItem`, `:2971`이하)과 같은 API, 새 디스크 조작 코드 없음.

### 데이터/아키텍처(제안)
- **이름 변환은 순수 함수로** — "규칙 + 원래 이름 목록 → 새 이름 목록". 파일시스템
  접근 없이 문자열 변환만이라 MTA 시험으로 바로 검증 가능.
- **미리보기 타입을 새로 만들어야 한다.** 기존 `IFileOperationEngine.PreviewAsync` →
  `FileOperationPreview`(`IFileOperationEngine.cs:26`)는 "개수·충돌 요약"이지 "파일명별
  전/후 목록"이 아니다(팔로업 보고서 §4에서 확인) — 재사용이 아니라 `RenamePreviewRow`
  같은 작은 타입을 새로 만드는 쪽이 맞다. 다만 **"계산 → 미리보기 → 확정 실행"이라는
  흐름 자체**는 그 기능이 이미 쓰는 것과 같은 모양이라, 그 UX 패턴(다이얼로그 구조·확인
  버튼 배치)은 참고할 수 있다.
- **부분 실패 정책은 이미 이 앱의 확립된 관례다 — 그대로 따르는 쪽을 제안한다.**
  `IFileOperationEngine.cs:32` "항목 1건의 결과. **부분 실패가 기본이다**(§5)." —
  `OperationItemResult`가 항목마다 `Succeeded/Skipped/Failed` + 이유를 담고,
  `FileOperationReport`가 그걸 모아 전체 결과로 낸다(§4.7·§5). 배치 리네임도 같은 모양
  (항목별 성공/실패 + 이유를 실행 후 목록으로 보여준다)으로 가면, 사용자가 이미 복사/이동
  에서 보는 것과 같은 정신 모델을 그대로 쓴다 — 리네임만 "전체 롤백"으로 다르게 갈 이유가
  없다.

### 미결(JH 결정)
- 세 규칙 유형(찾기/바꾸기·번호 매기기·대소문자)이 V1으로 충분한지, 정규식까지 원하는지.
- 이름 충돌 시 확인 버튼만 막을지, 자동으로 접미사(`(1)` 등)를 붙여 우회하는 옵션을 줄지.

## 공통 미결 — 구현 순서와 별개로 정해야 할 것

- 셋 다 새 UI 요소가 필요하다 — ①은 행 배지, ②는 새 결과 화면, ③은 새 다이얼로그+
  미리보기 표. 디자인(색·배치·문구)은 이 문서가 안 정했다.
