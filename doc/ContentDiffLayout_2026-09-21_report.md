# 내용 비교 창 레이아웃 재구성 + 헤더 클릭 열기 + 판 올림 (2026-09-21)

`doc/HandCheckFixes_2026-09-20_report.md`(커밋 `f9eb57d`)는 이미 커밋됐고 그 규약대로
손대지 않는다 — 이 문서는 그 라운드 손 확인이 이어지던 중, "⑦ 단어 단위 하이라이트"까지
확인한 뒤 JH가 화면 구조 자체를 다시 요구한 것부터 시작해, 이어진 다듬기(스크롤바
하나로·헤더 클릭 열기)와 판 올림 요청까지 같이 다룬다. 번호는 그 문서의 이어(⑧).

## ⑧ 내용 비교 창 — 두 판처럼(가로 스크롤 독립, 세로 공유, 경로 헤더, 폭 조절) 재구성

**증상:** ⑦(단어 단위 하이라이트)까지 확인한 뒤 화면 자체가 문제라는 지적 — 왼쪽·오른쪽이
하나의 가로 스크롤을 같이 써서, 한쪽 긴 줄 때문에 스크롤하면 반대쪽도 같이 밀려나 보기
불편했다. 또 위쪽엔 타일 라벨만 있어 "왼쪽이 정확히 어느 파일인지" 애매했다.

**JH가 요구한 것, 그대로:**
1. 왼쪽·오른쪽이 각자 독립된 가로 스크롤(하나 스크롤해도 반대쪽 안 움직임).
2. 세로 스크롤은 둘이 공유(같이 움직임).
3. 위쪽에 각자 실제 경로 표시.
4. 창 크기에 맞춰 안쪽 두 판도 크기 조절(폭 조절 가능하게).
5. 바깥 전체 창에는 가로 스크롤이 안 생기게.

**고침:** `ListView` 하나로 양쪽을 한 행씩 그리던 것을 걷어내고, `ScrollViewer` 두
개(`LeftScroll`/`RightScroll`, 각자 `ItemsControl`)로 다시 짰다:
- 가로는 각 `ScrollViewer`가 독립으로 처리(`HorizontalScrollBarVisibility="Auto"`,
  서로 안 건드림).
- 세로는 code-behind가 맞춘다 — 한쪽이 `ScrollChanged`로 세로 오프셋이 바뀌면 반대쪽에
  `ScrollToVerticalOffset`로 그대로 옮긴다(가로 오프셋은 안 건드림). 재진입 방지 플래그
  (`_syncingScroll`)로 서로 부르며 되도는 것을 막았다.
- 경로 헤더 둘 + 가운데 `GridSplitter`를 같은 `Grid`(같은 `ColumnDefinitions`)에 둬서,
  스플리터를 끌면 헤더·본문 폭이 같이 따라간다.
- 바깥 열 폭이 전부 `*`(별표)라 창 폭에 맞춰 자동으로 나뉘고, 넘치는 내용은 안쪽
  `ScrollViewer`만 맡는다 — 바깥엔 가로 스크롤이 생길 자리 자체가 없다.
- 헤더는 타일 라벨뿐 아니라 실제 전체 경로(`item.FullPath`/`counterpart.FullPath`,
  `MainViewModel.OnCompareContentRequested`에서 이미 갖고 있던 값)를 붙여
  `"{라벨} — {경로}"`로 보여준다. 길면 말줄임(`TextTrimming="CharacterEllipsis"`) +
  툴팁으로 전체를 볼 수 있게 했다.

**advisor가 잡은 실제 버그 하나:** 각 행의 배경을 "빈 줄도 판 너비만큼 칠해지게" 하려고
`MinWidth`를 그 판의 `ScrollViewer.ActualWidth`에 묶었는데, `ActualWidth`는 세로
스크롤바가 차지하는 폭까지 포함한 값이다 — 내용이 짧아도 그 차이만큼 넘쳐서 안 필요한
가로 스크롤바가 생길 수 있었다. `ViewportWidth`(스크롤바 제외한 실제 보이는 폭)로
바꿔 고쳤다.

**advisor가 남긴 손 확인 항목(자동 시험이 못 보는 것, 셋):**
1. **가상화 없음.** `ListView`(내부적으로 가상화)에서 `ItemsControl`(가상화 없음)로
   바꿨다 — 5MB 상한 안에서도 줄 수가 수만 줄일 수 있는 파일(예: 압축된 로그)을 열면
   창을 여는 순간 그만큼의 화면 요소를 한꺼번에 만든다. **큰 텍스트 파일로 실제 열어보고
   느려지는지부터 확인해달라** — 느리면 가상화를 다시 넣어야 하는데, 그러면 지금 픽셀
   단위인 세로 스크롤 동기화도 항목 단위로 다시 짜야 해서 미리 손대지 않았다.
2. `MinWidth` 수정 자체가 실제로 짧은 줄에서 불필요한 가로 스크롤바를 안 만드는지, 특히
   스플리터로 폭을 끈 직후에도.
3. 왼쪽·오른쪽 줄 높이가 서로 다르면(예: 한쪽은 영문, 한쪽은 한글이라 글꼴 대체로 줄
   높이가 달라지면) 세로 동기화가 숫자로는 맞아도 화면에서는 줄이 어긋나 보일 수 있다 —
   `NoWrap`이라 웬만하면 한 줄=한 높이겠지만, 한글/영문 섞인 실제 파일로 확인해달라.

**시험:** `ContentDiffWindowConstructionTests.cs`에 1개 추가
(`HeadersShowTheActualFilePath`) — 헤더가 타일 라벨이 아니라 실제 경로 문자열을
포함하는지. 기존 시험 2개는 새 생성자 시그니처(경로 인자 추가)에 맞춰 갱신, 옛
`RowList`(단일 `ListView`) 참조는 `LeftList`/`RightList`(각자 `ItemsControl`)로
바뀌었다. 레이아웃·스크롤 동기화·가상화 자체는 자동 시험이 못 닿는다 — 위 셋이 전부
손 확인 몫이다.

### 다듬기 — 세로 스크롤바를 하나만 보이게 (JH 재지적, 09-21)

**지적:** "이럴거면 스크롤바는 하나만 두는 게 낫지 않음? 가운데 하나만." 왼쪽·오른쪽
세로 위치가 어차피 항상 같이 움직이는데, 막대를 두 개(양쪽 각자)씩 보여주는 건
군더더기였다.

**고침:** 왼쪽 판(`LeftScroll`)은 그대로 두고, 오른쪽 판(`RightScroll`)의
`VerticalScrollBarVisibility`를 `Auto`에서 `Hidden`으로 바꿨다 — 막대만 안 보일 뿐
스크롤 기능(휠·프로그램 호출)은 그대로 살아 있다. 왼쪽 판이 가운데 `GridSplitter`
바로 옆이라, 남은 막대 하나가 자연히 두 판 "가운데" 경계에 선다 — 새 열을 만들거나
스플리터의 드래그 폭 계산을 건드릴 필요가 없었다.

시험은 추가하지 않았다 — 스크롤바 시각적 표시 여부는 `VerticalScrollBarVisibility`
값 하나 바꾼 것뿐이라 기존 생성 시험(창이 안 죽는지)의 범위 밖이고, "정말 하나만
보이는지·오른쪽 위에서 휠 굴려도 왼쪽이 따라오는지"는 화면으로만 확인된다.

### 추가 — 경로 헤더를 누르면 그 파일이 열림 (JH 요청, 09-21)

**요청:** "상단 파일명에서 바로 해당 파일을 열 수 있게도 해주고."

**고침:** 헤더는 이미 파일 목록 항목이 아니라 하나뿐인 정적 글자라 더블클릭을 요구할
이유가 없다고 보고, **한 번 누르면** 그 파일을 OS 기본 프로그램으로 연다 — 파일 목록
더블클릭이 쓰는 것과 같은 통로(`IShellLauncher.Open`)를 그대로 재사용했다. 누를 수
있는 자리라는 걸 알리려고 커서를 손 모양으로 바꾸고, 마우스를 올리면 밑줄이 붙게 했다.
`ContentDiffWindow` 생성자에 `Action<string> openFile` 인자를 새로 받는다 —
`DuplicateFinderWindow`가 `revealInExplorer` 콜백을 받는 것과 같은 결이다.
`MainViewModel.OnCompareContentRequested`에서 `path => _shell.Open(path)`를 넘긴다 —
`DuplicateFinderWindow` 호출부가 반환값(성공/실패 문구)을 그냥 버리는 것과 똑같이,
여기도 실패 메시지를 따로 안내하지 않는다(기존 관례 그대로, 새로 바꾸지 않음).

**시험:** 생성자가 콜백을 받아 두 헤더에 거는 것까지는 기존 생성 시험들이 이미 덮는다
(창이 죽지 않는지). **실제로 눌렀을 때 그 콜백이 맞는 경로로 불리는지는 시험하지
않았다** — `MouseLeftButtonUp`은 `MouseButtonEventArgs`(진짜 `MouseDevice`가 있어야
만들어짐)를 요구해서, `DuplicateFinderWindowConstructionTests`가 더블클릭을 안
시험하기로 한 것과 같은 이유로 손 확인 몫이다.
